# Requirements Document

## Introduction

TAK Team Manager currently runs at proof-of-concept quality. A source-level audit of `server/` and `client/` against the documented intent in `README.md`, `ARCHITECTURE.md`, and `requirements.md` found significant gaps between what is documented and what is implemented: dead/duplicated authentication code, hardcoded development IP addresses shipped in the production frontend bundle, a schema/code column-name mismatch that is silently swallowed by fallback `try/catch` blocks, an access-request approval flow that is a no-op stub, a sync worker whose throughput cannot plausibly meet the documented 50,000-user bulk-operation target, zero automated tests despite Jest being configured, `console.log`-based logging with no correlation IDs despite ARCHITECTURE.md claiming structured JSON logging, and multi-step Authentik+database operations that run without transactional safety.

This document specifies the requirements to bring TAK Team Manager from PoC to production quality. Each requirement is grounded in a specific, observed gap in the current implementation rather than generic best practice. Requirements are organized by concern area: Authentication & Session Security, Code and Configuration Hygiene, Input Validation & Injection Prevention, Secrets Management, Rate Limiting & Abuse Prevention, Process Resilience & Error Handling, Sync Worker Reliability, Automated Testing, Observability, Configuration Validation, Database Schema Integrity, Transactional Data Integrity, Deployment Readiness, Performance & Scale, Feature Completeness, Undelivered Documented Features (vendor time-limited channel access, deployment-scoped overseas channel self-service, and channel creation approval, each promised by TAK.NZ's user-facing documentation but absent from the current codebase), Centralized Authorization Architecture, Data Retention, TAK Server Integration, Device Provisioning, Document Management, Bulk Operations, Communications, Audit and Compliance Tooling, and Configuration Surface.

This spec is scoped to application-level production-readiness: the `server/` and `client/` code, database schema, automated tests, container image, and local/dev deployment via `docker-compose`. It intentionally does not cover infrastructure-as-code orchestration for deploying TAK Team Manager into the broader TAK.NZ AWS environment, such as AWS CDK stacks, Secrets Manager wiring, VPC/networking, or ECS service/task orchestration matching the pattern already established in sibling repos like `auth-infra`; that production infrastructure deployment is intentionally tracked as a separate, future spec. Requirement 19's "production-oriented deployment artifact" language is deliberately generic (an ECS task definition, a Terraform/CDK snippet, or an equivalent) so that it does not presuppose the eventual CDK-based deployment approach; the future infrastructure spec should instead reference this repo's Dockerfile, health check endpoints (Requirement 14), TAK Server integration credentials (Requirement 26), and settings/secrets surface (Requirement 32) as its inputs.

## Glossary

- **App**: The Express.js web API process defined in `server/index.js`, serving both the REST API and the built React client.
- **Client**: The React single-page application in `client/src`.
- **Sync_Worker**: The standalone Node.js process in `server/workers/syncWorker.js` that consumes the `sync_operations` queue and performs all Authentik write operations.
- **Authentik**: The external OAuth2/LDAP identity provider that TAK Team Manager integrates with via its REST API v3.
- **Sync_Operation**: A row in the `sync_operations` table representing a queued, asynchronous action against Authentik (e.g. `add_user_to_group`).
- **Database**: The PostgreSQL instance accessed via the connection pool in `server/config/database.js` (App) and the dedicated pool in `server/workers/syncWorker.js` (Sync_Worker).
- **Access_Request**: A row in the `access_requests` table representing a pending request for account creation, team change, role change, or name change, processed by `RequestApprovalService`.
- **Global_Manager**: A user whose cached `is_admin`/`is_global_manager` flag is true, derived from Authentik group membership in `TakTeamManager_Admin`.
- **JWT_Token**: The signed token issued in `server/routes/auth.js` after OAuth2 callback, used by the Client for all authenticated API calls.
- **Health_Endpoint**: The `GET /health` route in `server/index.js`.
- **Config_Validator**: A startup-time component responsible for validating required environment variables before the App or Sync_Worker begin accepting work.
- **Channel**: A row in the `channels` table (or, for global channels, the `bch_channels`/`region_channels` tables), each mapped to one or more Authentik LDAP groups, representing a named communication group a user can be assigned to.
- **Vendor_User**: A user record (`users.is_vendor`) representing a vendor or technical support person, who by default has access only to the base `VND` Channel and no regional or organisation Channel, per `user-docs/docs/concepts/channels.md`'s "Vendor channels" section.
- **Vendor_Channel**: A row in the proposed `vendor_channels` table representing the singleton base Vendor Channel (Authentik group `VND`) to which a Vendor_User is assigned by default per Requirement 21 Criterion 2, distinct from `bch_channels`, `region_channels`, `deployment_channels`, and team-scoped `channels`; at most one `vendor_channels` row may have `is_active` set to `true` at any time.
- **Vendor_Channel_Grant**: A row (proposed `vendor_channel_grants` table) recording that a Vendor_User has been granted access to a specific non-team Channel, either for a bounded duration (`expires_at`) or until manually revoked, along with which Global_Manager granted or revoked it and when.
- **Deployment_Channel**: A row (proposed `deployment_channels` table) representing an `Overseas -` prefixed Channel created for a specific overseas deployment, distinguished from the existing BCH and Region global channel types, and carrying an optional `deployment_end_date` after which it is automatically deactivated; a Deployment_Channel with no `deployment_end_date` is a standing Pacific-partner channel that is never automatically deactivated.
- **Deployment_Coordinator**: A user authorized to request creation of a Deployment_Channel, as described in `user-docs/docs/concepts/channels.md`'s "Overseas deployment channels" section.
- **Domestic_Mission_Channel**: A Deployment_Channel (per Requirement 22) whose `name` matches the `[COUNTRY]-[FUNCTION]-[REGION]-[SUFFIX]` naming pattern (e.g. `AUS-FIRE-STL-2026`), consistent with the callsign-adjacent format documented in `user-docs/docs/concepts/callsigns.md`, rather than the `Overseas - ` prefix; it represents a temporary, mission-scoped Channel for a foreign partner embedded in a domestic regional response, as described in `user-docs/docs/concepts/channels.md`'s "Foreign partner channels" section, and always has a non-null `deployment_end_date`.
- **Channel_Request**: A row (proposed `channel_requests` table) representing a pending, team-admin-submitted request to create a custom team Channel that has not yet been approved, distinct from the existing Access_Request used for user access requests.
- **Permission_Registry**: A single module (proposed `server/config/permissions.registry.js`) mapping every mounted route path and HTTP method combination to its required permission identifier(s) and to role-based default permission sets, replacing scattered per-route `is_global_manager`/`Team.isAdmin` checks.
- **Authorization_Middleware**: The middleware component (residing in or invoked from `server/middleware/auth.js`) that consults the Permission_Registry on every incoming request to determine whether the requesting user holds the permission(s) required for the requested route path and HTTP method.
- **Retention_Policy**: A configurable rule, applied to the `sync_operations` table and to the `audit_logs` table, that defines the maximum age or terminal-state condition beyond which rows become eligible for deletion or archival.
- **Retention_Cleanup_Job**: A periodic process, run by or alongside the Sync_Worker, that applies the Retention_Policy to the `sync_operations` table and to the `audit_logs` table, deleting or archiving eligible rows.
- **TAK_Server**: The external TAK Server (Marti API) instance that TAK Team Manager optionally integrates with for certificate lifecycle operations, distinct from and in addition to the existing, required Authentik integration; enabled by configuring `TAK_SERVER_URL` and a set of mutual TLS client credentials.
- **Team_Owned_Device**: A user record (`users.is_team_device`) representing a device-only, non-human account (e.g. shared or apparatus equipment) provisioned with a synthetic, non-deliverable email address so that no OIDC login can be completed against it, distinguished from a human team member by its `is_team_device` flag and `device_label`.
- **MOU_Document**: A row in the proposed MOU_Document table representing a serverwide (`team_id IS NULL`) or team-specific document that a team or a Global_Manager may be required to sign or countersign.
- **MOU_Signature**: A row in the proposed MOU_Signature table recording that a specific MOU_Document has been signed, either via an in-app e-signature or an uploaded scanned copy, by a signing user or team, and optionally countersigned by a Global_Manager.
- **Public_Route_Registry**: A single module (proposed `server/config/publicRoutes.js`) enumerating every route path and HTTP method combination that is intentionally reachable without authentication, consulted before the `authenticateToken` middleware would otherwise apply.

## Requirements

### Requirement 1: Remove Dead and Duplicated Authentication Code

**User Story:** As a maintainer, I want unused authentication code removed from the repository, so that there is a single, auditable authentication code path with no risk of a stale or vulnerable flow being reintroduced.

#### Acceptance Criteria

1. THE Repository SHALL contain exactly one server-side OAuth2 authentication route module mounted at `/api/auth` in `server/index.js`.
2. THE Repository SHALL NOT contain `server/routes/auth-backup.js` or any other file that duplicates the OAuth2 login, callback, or token-exchange logic already implemented in `server/routes/auth.js` and is not mounted as a route in `server/index.js`.
3. WHERE a "silent authentication" (`prompt=none`) flow is implemented as a product feature, THE App SHALL implement it within the active `server/routes/auth.js` module, applying the same request-timeout value (currently 10000ms), `code` parameter validation, and error-redirect handling already used by the primary OAuth2 callback in that file.
4. THE App SHALL NOT embed any literal IP address or hardcoded hostname (e.g. `44.229.3.37`) in server-side or client-side source files; all environment-specific hosts SHALL be read from configuration (`APP_URL`, `FRONTEND_URL`, or equivalent).
5. THE App SHALL NOT treat correct `APP_URL`/`FRONTEND_URL` host configuration alone (per Criterion 4) as sufficient evidence that authentication is functional; THE App SHALL additionally verify, at startup or via a documented health check, that the single active OAuth2 authentication route module identified in Criterion 1 is mounted and reachable, such that a correctly configured `APP_URL`/`FRONTEND_URL` with no functional auth route does not silently pass as compliant.

### Requirement 2: Eliminate Hardcoded Development Endpoints from the Client Build

**User Story:** As an operator deploying TAK Team Manager to a new environment, I want the client to derive all backend URLs from build/runtime configuration, so that the production login flow works correctly without manual code edits.

#### Acceptance Criteria

1. THE Client SHALL NOT contain a hardcoded backend host, port, or IP address in `client/src/services/api.js`, `client/vite.config.js`, or any other client source file.
2. THE Client SHALL derive the backend base URL used for API requests, `authAPI.login()`, and `authAPI.silentLogin()` from a single configurable source (e.g. a build-time environment variable such as `VITE_API_BASE_URL`, defaulting to a same-origin relative path when unset).
3. WHEN `authAPI.login()` or `authAPI.silentLogin()` is invoked, THE Client SHALL construct the target URL using the configured backend base URL from Criterion 2.
4. WHEN the Vite development server starts and a backend proxy target is required (i.e. only when Vite is running in development mode via `vite dev`/`vite serve`, and not as part of building or serving the production client bundle), THE Client SHALL read the proxy target from a `.env`-provided variable (e.g. `VITE_DEV_PROXY_TARGET`); IF that variable is unset, THEN THE Client SHALL default to `http://localhost:3000` rather than a literal external IP address.
5. WHEN the Client's `postMessage` origin check for the silent-login popup is evaluated, THE Client SHALL compare the message origin against the configured backend base URL's origin (from Criterion 2) rather than a hardcoded string, and SHALL discard the message if the origins do not match.
6. IF the silent-login popup does not deliver a `postMessage` response within 5 seconds of being opened, THEN THE Client SHALL close the popup and treat silent login as failed, falling back to the standard interactive login flow.
7. IF the configured backend base URL (Criterion 2) is not a syntactically valid absolute URL or relative path at application startup, THEN THE Client SHALL log a descriptive configuration error to the browser console and SHALL NOT attempt to construct login or API request URLs from it.
8. WHEN the configured backend base URL (Criterion 2) is a syntactically valid absolute URL or relative path at application startup, THE Client SHALL proceed to construct login and API request URLs from it normally, such that the error-logging and construction-avoidance behavior described in Criterion 7 SHALL NOT occur.

### Requirement 3: Secure JWT Issuance, Storage, and Revocation

**User Story:** As a security-conscious operator, I want authentication tokens handled using current best practice, so that session hijacking and stale-access risks are minimized.

#### Acceptance Criteria

1. WHEN the OAuth2 callback in `server/routes/auth.js` completes successfully, THE App SHALL deliver the JWT_Token to the Client without placing it in a URL query parameter that would be recorded in browser history, server access logs, or `Referer` headers.
2. THE App SHALL issue the JWT_Token as an `httpOnly`, `Secure`, `SameSite=Lax` (or stricter) cookie, such that the token value is never exposed to client-side JavaScript via `document.cookie` or any response body field.
3. WHEN a user calls `POST /api/auth/logout` with a valid JWT_Token, THE App SHALL invalidate that token (e.g. via a server-side revocation list or short-lived token plus refresh-token rotation) such that any subsequent request using that same token is rejected with HTTP 401, and SHALL clear the token cookie on the response.
4. IF a user calls `POST /api/auth/logout` without a valid JWT_Token (missing or already-invalid token), THEN THE App SHALL still clear any token cookie present on the response and SHALL return a success response, without erroring.
5. IF the `JWT_SECRET` environment variable is unset or shorter than 32 characters at startup, THEN THE App SHALL fail to start, SHALL log a descriptive configuration error identifying `JWT_SECRET` as the cause, and SHALL exit with a non-zero status code.
6. IF the `JWT_EXPIRES_IN` environment variable is unset, non-numeric, or represents a duration shorter than 5 minutes or longer than 30 days at startup, THEN THE App SHALL fail to start and SHALL log a descriptive configuration error identifying `JWT_EXPIRES_IN` as the cause.

### Requirement 4: Enforce Team and Global Admin Authorization Consistently

**User Story:** As a team administrator, I want administrative actions to be gated by verified authorization checks, so that non-admin users cannot create, modify, or delete teams and channels they do not control.

#### Acceptance Criteria

1. WHEN a user submits `POST /api/teams` with a `parentTeamId`, THE App SHALL verify that the requesting user is an admin of the parent team (via `Team.isAdmin`) or a Global_Manager before creating the sub-team. IF the requesting user is neither an admin of the parent team nor a Global_Manager, THEN THE App SHALL reject the request with an error response indicating insufficient authorization and SHALL NOT create the sub-team.
2. THE App SHALL NOT contain authorization logic marked with a `TODO` placeholder that allows any authenticated user to perform an administrative action (e.g. the current `// TODO: Implement proper team admin checking when team memberships are set up` in `server/routes/teams.js`).
3. IF `Team.isAdmin` or an equivalent authorization check throws an error, THEN THE App SHALL treat the request as unauthorized (fail closed), SHALL respond with an error response indicating an authorization failure without exposing internal error details, and SHALL log the failure with the requesting user identifier, the team identifier, and an error category value that distinguishes an authorization-check exception from a database connectivity failure.
4. WHEN a request targets a Global_Manager-only endpoint (e.g. `/api/global-channels/bch`, `/api/global-channels/region`, credential retrieval, channel deletion), THE App SHALL verify `is_global_manager` via a server-side check on every request, independent of any Client-side route guarding. IF the requesting user's `is_global_manager` flag is false, THEN THE App SHALL reject the request with an error response indicating that Global_Manager access is required and SHALL NOT perform the requested action.
5. WHEN a user submits `POST /api/teams` without a `parentTeamId` (creating a top-level team), THE App SHALL verify that the requesting user is a Global_Manager before creating the team. IF the requesting user is not a Global_Manager, THEN THE App SHALL reject the request with an error response indicating insufficient authorization and SHALL NOT create the team.
6. IF the server-side `is_global_manager` check required by Criterion 4 throws an error or fails to execute for any reason, THEN THE App SHALL treat the request as unauthorized (fail closed), SHALL reject the request with an error response indicating an authorization failure without exposing internal error details, and SHALL log the failure with the requesting user identifier and an error category value that distinguishes an authorization-check exception from a database connectivity failure, mirroring the fail-closed pattern already required for `Team.isAdmin` under Criterion 3.

### Requirement 5: Parameterize and Sanitize All Data Paths That Reach the Database or the DOM

**User Story:** As a security reviewer, I want all SQL execution and HTML rendering paths to be free of injection risk, so that user-supplied or admin-supplied content cannot execute unintended SQL or scripts.

#### Acceptance Criteria

1. THE App SHALL NOT interpolate caller-controlled values directly into SQL table or column names.
2. WHEN dynamic table selection is required (e.g. `GlobalChannelService.deleteGlobalChannel`'s `${table}` interpolation), THE App SHALL validate the value against an explicit allow-list of permitted table names at the point of query construction, independent of any validation performed by the calling route.
3. IF a value used for dynamic table or column selection does not match the explicit allow-list, THEN THE App SHALL reject the operation without executing the query and SHALL return an error indication to the caller.
4. WHERE an admin-editable field is rendered as raw HTML on any public-facing page, THE App SHALL restrict the rendered HTML to a documented safe subset of tags and attributes that, at minimum, excludes `<script>`, `<iframe>`, `<object>`, and `<embed>` tags, all event-handler attributes (e.g. `onclick`, `onerror`), and `javascript:` scheme URLs in `href` or `src` attributes.
5. IF admin-editable HTML content submitted for storage or rendering contains tags or attributes outside the documented safe subset defined in Criterion 4, THEN THE App SHALL strip or reject the disallowed portions before persisting or rendering the content, such that the disallowed tags, attributes, or script content never appear in the rendered DOM.
6. WHEN a `config_value` persisted via `SiteConfig.update` is rendered via `dangerouslySetInnerHTML` on the Client (e.g. `request_access_footer`), THE App SHALL ensure the HTML content injected into the DOM contains only tags and attributes within the safe subset defined in Criterion 4, with all other tags, attributes, and inline script content removed or escaped, regardless of whether sanitization is performed on write, on render, or both.
7. THE App SHALL apply consistent `express-validator` sanitization (trim, escape where rendered as HTML, and a maximum length of 1000 characters per field unless a stricter limit is defined for that field) to all user-supplied and publicly-submitted fields, including the unauthenticated `POST /api/requests/team-access` endpoint.
8. IF a user-supplied or publicly-submitted field fails required sanitization or exceeds its configured maximum length, THEN THE App SHALL reject the request without persisting the field value and SHALL return an error indication identifying the invalid field(s).

### Requirement 6: Protect Secrets and Remove Plaintext Credential Storage

**User Story:** As an operator responsible for compliance, I want service account and integration credentials handled without plaintext storage, so that a database compromise does not directly expose usable Authentik credentials.

#### Acceptance Criteria

1. THE App SHALL encrypt BCH service account passwords before persisting them to the `bch_channels.service_account_password` column, using an application-managed encryption key or an external secrets store, such that the stored column value is never the plaintext password, matching the existing code comment "In production, this should be encrypted" in `GlobalChannelService.createBchChannel`.
2. WHEN BCH channel credentials are retrieved via `GET /api/global-channels/bch/:channelId/credentials`, THE App SHALL decrypt the credential only at the point of building the response, SHALL NOT log the decrypted plaintext value at any point, and SHALL log the access as an auditable event recording the requesting user's identifier, the accessed channel's identifier, and the access timestamp.
3. IF decryption of a BCH service account password fails when handling `GET /api/global-channels/bch/:channelId/credentials`, THEN THE App SHALL return an error response without exposing the encrypted ciphertext or decryption error internals, and SHALL log the failure with the channel identifier and requesting user identifier.
4. WHERE the App is started with `NODE_ENV=production`, THE Config_Validator SHALL require that `AUTHENTIK_ADMIN_TOKEN`, `JWT_SECRET`, `DB_PASSWORD`, and any configured AWS credentials are sourced from a secrets manager or equivalent mechanism rather than only from a plain `.env` file, consistent with the "Secrets Manager for credentials" claim in `README.md`'s Deployment section. IF the App is started with `NODE_ENV=production` and the configured secrets manager (or equivalent mechanism) is unreachable or fails to return a required secret at startup, THEN THE App SHALL fail to start and SHALL exit with a non-zero status code, rather than falling back to a plain `.env` value for that secret.
5. THE App's dependency manifest SHALL NOT declare `aws-sdk` (v2); THE App SHALL implement `EmailService` using a maintained AWS SDK v3 client or an equivalent supported SDK.
6. THE Repository's `.env.example` SHALL document every environment variable read by the running code, including `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, and `SES_FROM_EMAIL` consumed by `EmailService.js`, and SHALL NOT list any variable that is not read by any code path (e.g. the unused `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS` block).

### Requirement 7: Apply Endpoint-Appropriate Rate Limiting

**User Story:** As an operator, I want sensitive and public-facing endpoints protected by rate limits proportional to their abuse potential, so that a single global limiter does not leave login, request-access, and email-verification endpoints exposed to abuse.

#### Acceptance Criteria

1. THE App SHALL apply a dedicated rate limit of no more than 20 requests per IP address per 15-minute window to `POST /api/requests/team-access`, `GET /api/requests/verify/:token`, and the OAuth2 `/api/auth/*` routes, distinct from and stricter than the general 1000-requests-per-15-minute limiter currently applied uniformly in `server/index.js`.
2. WHEN the request-access rate limit is exceeded (more than 20 requests from a given IP address within a 15-minute window, or more than 5 requests associated with a given email address within a 60-minute window), THE App SHALL return HTTP 429, SHALL NOT send a verification email, and SHALL NOT create a new Access_Request row for the request that exceeded the limit.
3. THE App SHALL require a bot-mitigation challenge (e.g. CAPTCHA or equivalent) to be solved on every submission to the unauthenticated `POST /api/requests/team-access` endpoint, in addition to rate limiting.
4. IF the bot-mitigation challenge on `POST /api/requests/team-access` is missing or fails validation, THEN THE App SHALL reject the request with an error response indicating the challenge failed, and SHALL NOT create an Access_Request row or send a verification email.
5. THE App SHALL rate-limit `GET /api/auth/callback` and OAuth2 token-exchange failures to no more than 10 failed attempts per IP address per 15-minute window, to prevent brute-force enumeration of authorization codes.
6. IF the rate limit on `/api/auth/*` routes is exceeded, THEN THE App SHALL return HTTP 429 and SHALL NOT proceed with token exchange or any Authentik API call for the offending request.

### Requirement 8: Handle Process-Level Errors Without Crashing or Corrupting State

**User Story:** As an operator, I want the App and Sync_Worker to survive unexpected errors gracefully, so that a single failed operation or database blip does not take down the entire service.

#### Acceptance Criteria

1. THE App SHALL register `process.on('unhandledRejection', ...)` and `process.on('uncaughtException', ...)` handlers in `server/index.js`.
2. WHEN an `unhandledRejection` event occurs, THE App SHALL log the rejection reason and originating context via the structured logger (Requirement 13) and SHALL continue running without exiting.
3. WHEN an `uncaughtException` event occurs, THE App SHALL log the exception and its stack trace via the structured logger (Requirement 13) and SHALL perform a controlled shutdown (per Criterion 4) rather than continuing in a potentially corrupted state.
4. WHEN the App receives `SIGTERM`, `SIGINT`, or an `uncaughtException` requiring shutdown, THE App SHALL stop accepting new HTTP connections, allow in-flight requests up to 30 seconds to complete, close the database pool, and then exit; IF in-flight requests have not completed within 30 seconds, THEN THE App SHALL immediately proceed to close the database pool and exit without further waiting for those in-flight requests, rather than delaying closure or exit any further.
5. THE App's database pool (`server/config/database.js`) SHALL register a `pool.on('error', ...)` handler, matching the pattern already present in `server/workers/syncWorker.js`, so that an idle client error does not crash the process.
6. THE App SHALL configure an explicit maximum connection pool size for `server/config/database.js` via a configurable environment variable (e.g. `DB_POOL_MAX`, defaulting to 20) rather than relying on the `pg` library's default, sized for the documented scale target of up to 50,000 users.
7. WHEN any route handler's promise chain rejects without an explicit `.catch`, THE App SHALL ensure the global error-handling middleware still returns an error response to the client and logs the error via the structured logger (Requirement 13); fire-and-forget calls (e.g. `authentikSync.syncUsers().catch(console.error)`) SHALL route errors through that same structured logger instead of `console.error`.

### Requirement 9: Correct Sync Worker Retry, Backoff, and Payload Handling

**User Story:** As an operator relying on the Sync_Worker to keep Authentik in sync, I want retry and backoff behavior that is bounded and correct, so that failed operations neither retry forever with an overflowing delay nor silently stop being retried.

#### Acceptance Criteria

1. WHEN `handleOperationError` computes the next retry delay using exponential backoff, THE Sync_Worker SHALL cap the computed per-retry delay at a fixed maximum of 1 hour (3,600,000 ms), such that `Math.pow(2, retry_count)` combined with this cap always produces a valid, non-overflowing `next_retry_at` timestamp for any `retry_count` value up to `max_retries`.
2. THE Sync_Worker SHALL enforce a `max_retries` value of 48, replacing the current schema default of 100, so that the maximum possible cumulative retry duration (48 retries times the 1-hour per-retry delay cap) does not exceed the 48-hour retry window stated in `ARCHITECTURE.md`.
3. WHEN `executeOperation` receives a payload, THE Sync_Worker SHALL validate the payload against the expected field set and data types defined for its `operation_type` before use, rather than only checking `typeof`.
4. IF a payload fails validation against the expected shape for its `operation_type`, THEN THE Sync_Worker SHALL mark the Sync_Operation as permanently failed without incrementing `retry_count` or scheduling a `next_retry_at`, and SHALL record a validation-failure indication on the `sync_operations` row that is distinguishable from an Authentik API failure; THE Sync_Worker SHALL NOT schedule a retry for a payload-validation failure under any circumstance, even if other conditions on the same Sync_Operation would otherwise indicate the failure is retryable.
5. THE Sync_Worker SHALL remove verbose payload logging that prints raw operation payloads and user attribute values (potential PII) to standard output, replacing it with structured, level-gated logging as described in Requirement 13.
6. IF an Authentik API call within an operation handler (e.g. `addUserToGroup`, `createBchChannelGroups`) receives a non-2xx response, THEN THE Sync_Worker SHALL classify the failure as retryable (HTTP 5xx responses or network/timeout errors) or permanent (HTTP 4xx client errors such as "group not found"), SHALL record that classification on the `sync_operations` row, and SHALL NOT schedule a further retry for a failure classified as permanent. THE non-2xx retryable/permanent classification described in this Criterion SHALL apply only to non-2xx responses; a 2xx response SHALL NOT categorically preclude a retry being scheduled for that Sync_Operation WHERE a separate condition independently warrants one (e.g. a payload-validation failure per Criterion 4 detected after a 2xx response, or an application-level error embedded in a 2xx response body), such that the HTTP status code alone is not the sole determinant of retry eligibility.

### Requirement 10: Process Multiple Sync Operations Concurrently to Meet Documented Throughput

**User Story:** As an operator running bulk operations (e.g. assigning 50,000 users to global channels), I want the Sync_Worker to complete within the time documented in ARCHITECTURE.md, so that bulk operations are operationally usable.

#### Acceptance Criteria

1. THE Sync_Worker SHALL fetch a batch of pending `sync_operations` rows per polling cycle (minimum 10, maximum 500 rows per cycle), using `FOR UPDATE SKIP LOCKED` and a worker pool to process the batch concurrently, rather than the current single-row `LIMIT 1` fetch per 5-second poll; the per-cycle batch size SHALL be independent of the configured concurrency level defined in Criterion 3, and THE Sync_Worker SHALL NOT require the configured concurrency level to match or exceed the batch size. Rows within a fetched batch in excess of the configured concurrency level SHALL be processed sequentially, as concurrency slots become available, within that same cycle.
2. WHEN a bulk operation of exactly 50,000 queued `sync_operations` rows is enqueued and each corresponding Authentik call succeeds (via mocked Authentik responses in a load test), THE Sync_Worker SHALL cause all 50,000 rows to reach a `completed` status within 65 minutes of the enqueue timestamp, treating 60 minutes as the target consistent with the 30-60 minute window stated in `ARCHITECTURE.md`, and treating 65 minutes (a 5-minute buffer over that target) as the hard pass/fail threshold for the load test.
3. THE Sync_Worker SHALL expose a configurable concurrency level (e.g. `SYNC_WORKER_CONCURRENCY`), accepting an integer between 1 and 100 inclusive and defaulting to 10 if unset, so operators can tune throughput against Authentik's rate limits; THE configured concurrency level MAY be set lower than the per-cycle batch size defined in Criterion 1, allowing operators to choose conservative parallelism even when a larger batch size is configured.
4. WHERE multiple Sync_Worker instances run concurrently for horizontal scaling, THE Sync_Worker SHALL rely on the existing `FOR UPDATE SKIP LOCKED` row locking so that no two instances process the same `sync_operations` row (verified by an automated test running at least two concurrent worker instances against a shared queue and confirming each row's terminal status transition occurs exactly once).
5. WHILE processing operations concurrently, THE Sync_Worker SHALL NOT execute two pending `sync_operations` rows that target the same entity (e.g. the same `user_id` combined with the same group or channel) out of their enqueued order; such rows SHALL be serialized within the concurrent batch (e.g. by routing same-entity rows to the same worker or deferring the later row to the next cycle).

### Requirement 11: Reduce Authentik Sync Cost and Avoid Redundant Full-Dataset Fetches

### Requirement 17: Wrap Multi-Step Team, User, and Channel Operations in Transactions

**User Story:** As an operator, I want multi-step operations that touch both the database and Authentik to leave the system in a consistent state even when a step fails, so that partial failures do not silently desynchronize the database from Authentik or leave orphaned records.

#### Acceptance Criteria

1. WHEN `POST /api/users/create-and-add` executes its sequence of Authentik user creation, local user upsert, team membership inserts (including parent-team inheritance), and channel membership inserts, THE App SHALL wrap all database writes in a single transaction using one acquired client, committing only after all local writes succeed. IF any database write in that sequence fails, THEN THE App SHALL roll back the transaction and SHALL return an error response to the caller without leaving partial local records.
2. IF any step in a multi-step team/user/channel operation fails after the Authentik-side resource has already been created (e.g. the Authentik user was created but a subsequent database insert fails), THEN THE App SHALL first attempt a synchronous compensating action (e.g. delete the newly created Authentik user); IF that compensating action itself fails, THEN THE App SHALL enqueue a Sync_Operation to reconcile the discrepancy; in either case, THE App SHALL log the partial failure with the affected Authentik resource identifier, the failed step, and the compensation outcome.
3. WHEN `Team.delete` removes a team, THE App SHALL delete the team, its `team_memberships`, its `channels`, and its `channel_memberships` within a single transaction. IF any deletion within that transaction fails, THEN THE App SHALL roll back the transaction, SHALL leave the team and its associated records unchanged, and SHALL return an error response to the caller.
4. WHEN `Team.delete` successfully commits the deletion of a team's `channels`, THE App SHALL enqueue a Sync_Operation to remove the corresponding Authentik groups for those deleted channels, so that Authentik-side groups do not remain orphaned after the local records are deleted.
5. WHEN `TeamMembershipService.addUserToTeam` or `removeUserFromTeam` executes, THE App SHALL continue to use a single transactional client for all database writes (as it currently does) and SHALL additionally ensure that queuing the corresponding `Sync_Operation` rows occurs within that same transaction so that a queued operation is never orphaned by a rolled-back membership change.

### Requirement 23: Introduce a Channel Creation Approval Workflow for Teams

**User Story:** As a team administrator requesting an additional channel for my team, I want my request to go through an approval step, so that the "Channel management — creating or approving additional channels for your team" capability already promised in TAK.NZ's user-facing documentation is actually implemented, rather than the current behavior in `POST /api/channels/custom`, which creates a custom team channel immediately with no pending or approval state, unlike the existing `access_requests`/`RequestApprovalService` approval pattern used for user access requests.

#### Acceptance Criteria

1. THE Repository's schema SHALL add a `channel_requests` table recording at minimum a `team_id`, a `custom_suffix`, a `member_permissions` JSONB payload (matching the shape currently accepted directly by `POST /api/channels/custom`), a `requested_by` user id, a `status` (`pending`, `approved`, `denied`), a nullable `processed_by` user id, a nullable `processed_at` timestamp, and a nullable `denial_reason`.
2. WHEN a team admin who is not a Global_Manager submits a request to create a custom channel for their team, THE App SHALL insert a `channel_requests` row with `status` set to `pending` and SHALL NOT create the `channels` row or enqueue any Sync_Operation until the request is approved.
3. WHEN a Global_Manager submits a request to create a custom channel for a team, THE App SHALL create the `channels` row immediately, following the existing behavior of `POST /api/channels/custom`, without requiring an approval step.
4. THE App SHALL restrict approval and denial of a pending Channel_Request to a Global_Manager or to an admin (per `Team.isAdmin`) of the parent team of the `team_id` named on that Channel_Request, matching the authorization pattern already required for sub-team creation in Requirement 4 Criterion 1.
5. WHEN an authorized approver approves a pending Channel_Request, THE App SHALL, within a single transaction, set that Channel_Request's `status` to `approved` with `processed_by` and `processed_at` recorded, create the corresponding `channels` row, and enqueue the Sync_Operation(s) needed to create the associated Authentik group(s), mirroring the transactional-approval pattern already required for Access_Request approval in Requirement 18 Criterion 6.
6. IF creating the `channels` row or enqueueing the associated Sync_Operation(s) fails after a Channel_Request's `status` has been set to `approved` within the transaction described in Criterion 5, THEN THE App SHALL roll back the entire transaction so that the Channel_Request remains in `pending` status and can be retried, rather than leaving it `approved` without a corresponding channel having been created.
7. WHEN an authorized approver denies a pending Channel_Request, THE App SHALL set that Channel_Request's `status` to `denied` with `processed_by`, `processed_at`, and `denial_reason` recorded, and SHALL NOT create a `channels` row or enqueue any Sync_Operation for that request.
8. IF a request to approve or deny a Channel_Request targets a request whose `status` is not `pending`, THEN THE App SHALL reject the approval or denial with an error response indicating the request has already been processed, and SHALL NOT modify the `channel_requests` row.
9. WHEN a Channel_Request is submitted for a team that already has 3 channels (counting existing `channels` rows), THE App SHALL reject the request with an error response indicating the 3-channel-per-team limit has been reached and SHALL NOT insert a `channel_requests` row, consistent with the limit already enforced at creation time in Requirement 16 Criterion 6.

### Requirement 24: Centralize Route Authorization in a Deny-by-Default Permission Registry

**User Story:** As a security reviewer, I want route authorization consolidated into a single deny-by-default registry rather than scattered per-route checks, so that a newly added route can never ship without an authorization check, following the pattern observed in the related open-source project TAK-Portal, whose `permissions.registry.js` maps every route path and HTTP method to a required permission and denies any unmapped route at the middleware layer.

#### Acceptance Criteria

1. THE Repository SHALL contain a single Permission_Registry module (`server/config/permissions.registry.js`) that maps every route path and HTTP method combination mounted in `server/index.js` to a list of required permission identifiers, replacing the scattered inline `is_global_manager` and `Team.isAdmin` checks currently present across route handlers such as `server/routes/teams.js`.
2. THE Permission_Registry SHALL define, at minimum, two role-based default permission sets: a Global_Manager set containing every permission identifier defined in the registry, and a standard authenticated-user set containing only the minimal permission identifiers required for non-administrative routes.
3. WHEN an HTTP request reaches the Authorization_Middleware, THE Authorization_Middleware SHALL look up the request's route path and HTTP method in the Permission_Registry and SHALL permit the request only if the requesting user holds every permission identifier associated with that route path and HTTP method entry.
4. IF a request's route path and HTTP method combination has no corresponding entry in the Permission_Registry, THEN THE Authorization_Middleware SHALL reject the request with an error response indicating access is denied, and SHALL NOT invoke the underlying route handler, regardless of the requesting user's role.

THE Permission_Registry SHALL contain entries for the Global_Manager-only endpoints enumerated in Requirement 4 Criterion 4 (`/api/global-channels/bch`, `/api/global-channels/region`, the BCH credential-retrieval route, and the channel-deletion route), such that the authorization behavior required by Requirement 4 Criterion 4 is enforced through the Permission_Registry and the Authorization_Middleware rather than through a per-route inline check.
6. THE Repository SHALL contain an automated test that enumerates every route path and HTTP method mounted in `server/index.js` and asserts that each one has a corresponding entry in the Permission_Registry, failing the test if any mounted route is missing a registry entry.
7. IF a route handler is added to `server/index.js` after the automated test in Criterion 6 exists, and that route has no corresponding Permission_Registry entry, THEN THE automated test SHALL fail, and THE Authorization_Middleware SHALL deny requests to that route per Criterion 4, so that the omission is caught in CI rather than in production.

### Requirement 25: Enforce Bounded Retention on Sync_Operations and Audit Log Data

**User Story:** As an operator running TAK Team Manager at the documented 50,000-user scale, I want the `sync_operations` and `audit_logs` tables bounded by a retention policy, so that terminal-state rows do not accumulate indefinitely and degrade query performance, following the pattern observed in the related open-source project TAK-Portal, whose `auditLog.store.js` enforces a maximum on-disk size and proactively trims the oldest entries when that limit is approached.

#### Acceptance Criteria

1. THE App SHALL define a configurable retention threshold (e.g. `SYNC_OPERATIONS_RETENTION_DAYS`, defaulting to 90 days) for `sync_operations` rows whose status is `completed` or permanently failed, per the failure classification established in Requirement 9 Criterion 6.
2. THE Retention_Cleanup_Job SHALL NOT delete or archive a `sync_operations` row whose status is `pending` or `retrying`, regardless of that row's age.
3. THE Retention_Cleanup_Job SHALL run as its own independently scheduled process (which MAY be hosted within the same Node process as the Sync_Worker, or run as a separate scheduled process or cron job) and SHALL execute on a periodic schedule (e.g. once every 24 hours), deleting or archiving every `sync_operations` row that is both older than the configured `SYNC_OPERATIONS_RETENTION_DAYS` threshold and in a `completed` or permanently-failed state, regardless of whether the Sync_Worker's main polling loop is currently running, so that retention cleanup continues during Sync_Worker downtime for maintenance or after a crash.
4. THE App SHALL define a separate configurable retention threshold (e.g. `AUDIT_LOGS_RETENTION_DAYS`, defaulting to 365 days) for rows in the `audit_logs` table introduced in Requirement 21 Criterion 9, distinct from and longer than the `sync_operations` retention threshold defined in Criterion 1.
5. THE Retention_Cleanup_Job SHALL run as its own independently scheduled process (which MAY be hosted within the same Node process as the Sync_Worker, or run as a separate scheduled process or cron job) and SHALL execute on a periodic schedule (e.g. once every 24 hours), deleting or archiving every `audit_logs` row older than the configured `AUDIT_LOGS_RETENTION_DAYS` threshold defined in Criterion 4, regardless of whether the Sync_Worker's main polling loop is currently running, so that retention cleanup continues during Sync_Worker downtime for maintenance or after a crash.
6. IF a Retention_Cleanup_Job run raises an error while deleting or archiving `sync_operations` or `audit_logs` rows, THEN THE Sync_Worker SHALL log the failure via the structured logger (Requirement 13), SHALL NOT crash or exit the Sync_Worker process, and SHALL retry the Retention_Cleanup_Job on its next scheduled run.
7. WHERE the Retention_Cleanup_Job is implemented, THE App SHALL apply row-count-and-age-based deletion against the Database rather than the file-size-based trimming approach used by TAK-Portal's `auditLog.store.js`, since TAK Team Manager persists `sync_operations` and `audit_logs` in PostgreSQL rather than in a flat JSON file.

### Requirement 26: TAK Server Certificate Lifecycle Management

**User Story:** As an operator, I want revoking a user's or team's TAK Server certificates to be a reliable, verified operation rather than a manual out-of-band process, so that a revoked user or disbanded team cannot continue connecting to TAK Server on a certificate TAK Team Manager believes has already been revoked.

#### Acceptance Criteria

1. WHERE `TAK_SERVER_URL` is configured, THE Config_Validator SHALL additionally require that mutual TLS client credentials for TAK Server (either `TAK_API_P12_PATH` and `TAK_API_P12_PASSPHRASE`, or `TAK_API_CERT_PATH` and `TAK_API_KEY_PATH`) are present and non-empty at startup, and MAY additionally read an optional `TAK_CA_PATH`; IF `TAK_SERVER_URL` is unset, THEN THE Config_Validator SHALL NOT require any TAK Server credential variable, since this integration is optional and unlike the required Authentik integration.
2. IF `TAK_SERVER_URL` is configured but its required mutual TLS client credentials (per Criterion 1) are missing or empty at startup, THEN THE App or Sync_Worker SHALL log the specific missing variable name(s) and SHALL exit with a non-zero status code before the App binds to a port or the Sync_Worker begins polling `sync_operations`.
3. THE Repository SHALL contain a new service module (e.g. `server/services/TakServerService.js`) that lists all certificates known to TAK Server's Marti `certadmin` API, matches certificates to a target user by comparing each certificate's `creatorDn` field to that user's TAK username, and revokes the matched certificate ids via the Marti `certadmin` revoke API.
4. WHEN `TakServerService` completes a revoke API call for a set of targeted certificate ids, THE App SHALL re-query the TAK Server certificate list or revoked-list and SHALL mark the revocation operation successful only if every targeted certificate id is confirmed present in a revoked state in that re-queried result.
5. IF the re-query performed under Criterion 4 does not confirm every targeted certificate id as revoked, THEN THE App SHALL mark the revocation operation as failed, SHALL NOT report the operation as successful, and SHALL record which targeted certificate ids failed verification.

THE Repository's schema SHALL add a new `sync_operations.operation_type` value (e.g. `revoke_tak_certificates`), and THE App SHALL enqueue a Sync_Operation of that type WHEN a Global_Manager or a team admin (per `Team.isAdmin`) explicitly revokes a specific user's TAK Server certificates, and WHEN a user is removed from all teams, consistent with the existing "Removal Logic: Users without teams are removed from all channels" behavior documented in `ARCHITECTURE.md`.
7. WHEN a Global_Manager disables or deletes a team, THE App SHALL enqueue a single bulk Sync_Operation batch that revokes TAK Server certificates for every member of that team and every one of its sub-teams, fetching the TAK Server certificate catalog exactly once for the entire batch rather than once per user, consistent with the N+1-avoidance requirement already established in Requirement 11.
8. IF a request to list or revoke certificates against TAK Server fails because TAK Server is unreachable or returns an error, THEN THE Sync_Worker SHALL classify that failure as retryable per the failure classification already established in Requirement 9 Criterion 6, and SHALL NOT report the associated `revoke_tak_certificates` Sync_Operation as successful.
