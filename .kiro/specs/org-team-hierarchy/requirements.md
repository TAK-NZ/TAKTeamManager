# Requirements Document

## Introduction

TAKTeamManager already models a hierarchy of teams using a single `teams` table with a self-referencing `parent_team_id` foreign key (adjacency list), queried recursively (`server/models/Team.js`, `server/services/userAttributes.js`). Every row in that hierarchy is currently labelled "Team" in the UI, regardless of depth, and the hierarchy is otherwise unbounded and largely unconstrained beyond parent/child linkage.

This document specifies a rework of how that existing hierarchy is presented and constrained, without introducing a new database table or changing the underlying permission model:

1. The root of each hierarchy (a `teams` row with `parent_team_id IS NULL`) is relabelled "Organisation" in the UI; every level beneath it continues to be labelled "Team".
2. A fixed, system-wide maximum of 5 Team levels beneath an Organisation is enforced everywhere a Sub_Team can be created (a Team at the deepest permitted level cannot be given a further Sub_Team). This maximum is a constant, not a per-Organisation configurable setting: an individual Organisation may in practice only ever use 1-4 levels, but that is simply a consequence of nobody creating a deeper Sub_Team there, not a separate configured limit.
3. TAK colour and a Callsign_Suffix default-computation rule (`callsign_name_format`) become exclusively set at the Organisation level and are inherited (read-only) at every Team level beneath it, enforced server-side.
4. Team admin status becomes inherited downward: an admin of any ancestor Team (up to and including the Organisation) is treated as an admin of every descendant Team.
5. Callsign generation gains the ability to select a non-contiguous subset of hierarchy levels (rather than only a contiguous prefix) to include in a generated callsign, configured per Organisation. Every user's callsign gains a stable, always-admin-editable `callsign_suffix` value as its Name segment, defaulted from that user's Organisation's `callsign_name_format` rule at creation time but never silently recomputed afterward.
6. Organisation membership becomes bounded: a user can see another Organisation's existence, Teams, or members only if they are a Global_Manager. Within their own Organisation, a member can see every public Team's existence and details, but a private Team's existence, attributes, members, and admins are visible only to that Team's own members/admins (direct or inherited) and to Global_Managers -- and this restriction cascades to every Sub_Team beneath a private Team regardless of that Sub_Team's own visibility setting.
7. The existing CSV team-import feature is extended to carry `visibility` and `callsign_prefix` per row, to enforce Max_Team_Depth and Organisation-only colour/name-format inheritance identically to the single-team creation API, and to resolve each row's parent via an import-local row reference rather than by team name, so a single CSV can establish an entire multi-level Organisation hierarchy (for example, importing FENZ's Organisation row followed by its Te Ihu / Canterbury / Station 40 chain) in one pass, in any row order, without relying on team names being unique.

No new `organizations` table or new primary key type is introduced. The existing single-table `teams` hierarchy, its existing auto-provisioned channel and Authentik group behaviour, and its existing upward membership-inheritance mechanism (`team_memberships.inherited_from_team_id`) are unchanged except where explicitly stated below. Direct membership at the Organisation level remains permitted; no requirement in this document restricts it.

## Glossary

- **Team**: A row in the existing `teams` table. Every row in the hierarchy, at every depth, is a Team at the data-model level.
- **Organisation**: A Team whose `parent_team_id` is `NULL` (the root of a hierarchy). "Organisation" is a UI label applied to root Teams; it is not a distinct database entity or type.
- **Sub_Team**: A Team whose `parent_team_id` is not `NULL` (i.e. any non-root Team in a hierarchy).
- **Max_Team_Depth**: A fixed, system-wide constant equal to 5. No Team may exist at a Team_Depth greater than Max_Team_Depth. Max_Team_Depth is not stored per-Organisation and is not configurable by a Global_Manager; it is the same value everywhere in the App.
- **Team_Depth**: For a given Team, the number of `parent_team_id` links between it and its Organisation. An Organisation has a Team_Depth of 0; a direct child of an Organisation has a Team_Depth of 1; and so on.
- **Ancestor_Chain**: For a given Team, the ordered sequence of Teams from that Team's Organisation down to and including that Team itself, following `parent_team_id` links.
- **Callsign_Level_Selection**: The set of Team_Depth positions (each between 0 and Max_Team_Depth inclusive) whose `callsign_prefix` value is included when generating a callsign for a user, stored per Organisation.
- **Callsign_Generator**: The existing logic that computes a user's TAK callsign, colour, and role attributes from their Ancestor_Chain (`computeCallsignAttributes` in `server/services/userAttributes.js`).
- **Team_Admin**: A user who holds a direct (non-inherited) `team_memberships` row with `role = 'admin'` for a given Team, OR who holds such a row for any Team in that Team's Ancestor_Chain (inherited admin status, per Requirement 4).
- **Global_Manager**: A user whose cached `is_global_manager` attribute is true, consistent with its use elsewhere in this codebase (`server/config/permissions.registry.js`).
- **Team_Management_API**: The existing Express route handlers under `server/routes/teams.js`.
- **Team_Model**: The existing `Team` class in `server/models/Team.js`.
- **Org_Member**: A user who holds a direct or inherited `team_memberships` row for any Team within a given Organisation's hierarchy (i.e. any Team whose Organisation is that Organisation).
- **Visible_Branch**: For a given viewing user, a Team T is a Visible_Branch if EITHER T's `visibility` is `public` AND no Team in T's Ancestor_Chain (including T itself) has `visibility` set to `private`, OR the viewing user is a member (direct or inherited) or a Team_Admin (direct or inherited, per Requirement 4) of T or of any Team in T's Ancestor_Chain, OR the viewing user is a Global_Manager. A Team whose Ancestor_Chain contains a `private` Team is not a Visible_Branch for any other user, even if the Team itself is marked `public`.
- **Team_Import_Row**: A single row of a Team CSV import file, processed by the existing `BulkImportService.importTeams`/`importTeamRow`.
- **Callsign_Suffix**: A per-user value, stored on every user's record regardless of Organisation, used as the Name segment of every generated callsign (per Requirement 8). Auto-filled at the time a user is created from that user's Organisation's `callsign_name_format` default-computation rule (Requirement 11), and freely editable afterward by a Team_Admin or Global_Manager. Once set, a Callsign_Suffix is never silently recomputed by any other change (a name correction, an Organisation's `callsign_name_format` change, or an Organisation change) -- see Requirement 11.
- **TAK_Role**: A per-user attribute stored in `user_cache.tak_role` (and mirrored to Authentik's `takRole` user attribute), taking one of eight predefined values (Team Member, Team Lead, Sniper, Medic, Forward Observer, RTO, K9, HQ), consistent with the role labels already configurable under Admin -> Site Content -> Role Descriptions (`server/routes/settings.js`'s `ROLE_KEY_LABELS`). Defaults to "Team Member" for a newly created user; once set to any value (including the default), a TAK_Role is never silently recomputed by any other change -- see Requirement 13.
- **Member_List**: The existing members/admins tables rendered on the Team Detail page's Members and Team Admins tabs (`client/src/pages/TeamDetail.jsx`), and, per Requirement 6, any equivalent Client view of an Organisation's or Team's members introduced by that requirement.

## Requirements

### Requirement 1: Organisation Labelling in the UI

**User Story:** As a user of the Client, I want the top level of a team hierarchy to be called "Organisation" and every level beneath it to be called "Team", so that the hierarchy's structure is clear without implying that every level is the same kind of thing.

#### Acceptance Criteria

1. WHERE a Team's `parent_team_id` is `NULL`, THE Client SHALL label that Team "Organisation" in every page and control that names or refers to it (including, but not limited to, the Teams list page, the Team Detail page's header, breadcrumbs, and dialog titles).
2. WHERE a Team's `parent_team_id` is not `NULL`, THE Client SHALL label that Team "Team" in every page and control that names or refers to it.
3. THE Team_Management_API SHALL NOT rename any request field, response field, database column, route path, or identifier as a result of this requirement.
4. WHEN the Client's "Create Team" action is invoked without a parent Team selected, THE Client SHALL label the resulting entity "Organisation" in the creation dialog's title and submit button text.
5. WHEN the Client's "Create Team" action is invoked with a parent Team selected, THE Client SHALL label the resulting entity "Team" in the creation dialog's title and submit button text.

### Requirement 2: System-Wide Maximum Team Depth

**User Story:** As a Global_Manager, I want the App to prevent a Team hierarchy from nesting deeper than a fixed maximum, so that no hierarchy can grow to an unmanageable depth, without needing to configure a limit myself for every Organisation.

#### Acceptance Criteria

1. THE App SHALL enforce a single Max_Team_Depth value of 5, applied identically to every Organisation. Max_Team_Depth SHALL NOT be stored per-Organisation and SHALL NOT be settable or updatable by a Global_Manager or any other user.
2. WHEN a Team_Admin or Global_Manager requests creation of a Sub_Team beneath a given parent Team, THE Team_Management_API SHALL compute the Team_Depth the new Sub_Team would occupy (the parent Team's Team_Depth plus one) before creating the Sub_Team.
3. IF creating a Sub_Team would result in a Team_Depth greater than Max_Team_Depth, THEN THE Team_Management_API SHALL reject the request with a 400 response stating that Max_Team_Depth and SHALL NOT create the Sub_Team.
4. WHEN a Team's own Team_Depth equals Max_Team_Depth, THE Client SHALL disable and visually grey out that Team's "Add Sub-team" control, so a user cannot attempt to create a Sub_Team that the Team_Management_API would reject.
5. WHEN a Team's own Team_Depth is less than Max_Team_Depth, THE Client SHALL render that Team's "Add Sub-team" control as enabled.
6. An Organisation or Team that in practice has no Sub_Team deeper than some depth less than Max_Team_Depth (for example, an Organisation whose deepest Team is at Team_Depth 3) remains fully permitted; Criteria 1-5 constrain only the deepest possible Team_Depth, not the depth any individual Organisation's hierarchy must reach.

### Requirement 3: Organisation-Only TAK Colour and Callsign Suffix Default Format

**User Story:** As a Global_Manager, I want TAK colour and a default Callsign_Suffix format to be set once at the Organisation level and apply consistently to every Team beneath it, so that all members of an Organisation share a consistent colour, and every new member's Callsign_Suffix starts from a consistent, predictable default.

#### Acceptance Criteria

1. WHEN a Global_Manager creates an Organisation, THE Team_Management_API SHALL accept and store a TAK colour (`color`) and a Callsign_Suffix default-computation rule (`callsign_name_format`) value on that Organisation.
2. WHEN a Team_Admin or Global_Manager creates a Sub_Team, THE Team_Management_API SHALL set that Sub_Team's `color` and `callsign_name_format` to its Organisation's current `color` and `callsign_name_format` values, regardless of any `color` or `callsign_name_format` value supplied in the request. `callsign_name_format` at Sub_Team level exists only so its inherited value is visible; it is not separately consulted, since Requirement 11 governs Callsign_Suffix default computation solely from the Organisation's value.
3. IF a request to update a Sub_Team includes a `color` or `callsign_name_format` value, THEN THE Team_Management_API SHALL ignore that value and SHALL NOT change the Sub_Team's `color` or `callsign_name_format`.
4. THE Callsign_Generator SHALL read the `color` value used for a given user from that user's Organisation, consistent with its existing behaviour of reading this value from the root Team of a hierarchy. THE Callsign_Generator SHALL NOT read `callsign_name_format` when generating a callsign; per Requirement 8, the Name segment of a generated callsign is always that user's stored Callsign_Suffix, never computed live from `callsign_name_format`.
5. THE Client SHALL render the `color` and `callsign_name_format` fields as read-only on every Sub_Team's edit and creation views, displaying the inherited Organisation value.
6. THE Client SHALL render the `color` and `callsign_name_format` fields as editable on an Organisation's edit and creation views.
7. THE Team_Management_API SHALL leave the existing behaviour of the `callsign_prefix` field unchanged: each Team, at any Team_Depth, continues to accept its own `callsign_prefix` value at creation time, which remains immutable after creation, consistent with existing behaviour.
8. THE Team_Management_API SHALL accept a `callsign_prefix` value only if it is empty, or consists exclusively of letters (A-Z, case-insensitive) and digits (0-9); THE Team_Management_API SHALL NOT permit the `-` character within a `callsign_prefix` value (for example, "NZP" is a valid `callsign_prefix`; "NZ-POL" is not). This is stricter than `callsign_suffix` (Requirement 11 Criterion 3), which does permit `-`; a `callsign_prefix` value participates in the Team segment's no-separator concatenation (Requirement 8 Criterion 3) and, at Team_Depth 0, in the `-`-joined segment assembly (Requirement 8 Criterion 5), so a `-` embedded inside a `callsign_prefix` value would be visually indistinguishable from an intended segment boundary.
9. IF a `callsign_prefix` value supplied at Team creation, through any entry point including the CSV import described in Requirement 9, contains a character other than a letter or digit (including the `-` character), THEN THE Team_Management_API SHALL reject the request (or, for a CSV import row, reject that row) with a 400 response or row-level error identifying the disallowed character, and SHALL NOT create the Team.
10. THE Client SHALL enforce the character restriction described in Criterion 8 on the `callsign_prefix` input control at the point of entry, in addition to the Team_Management_API's own rejection of an invalid value.

### Requirement 4: Inherited Team Admin Status

**User Story:** As a Team_Admin of an Organisation or any Team within it, I want my admin status to apply automatically to every Team beneath the Team I administer, so that I do not need a separate admin membership row in every descendant Team to manage them.

#### Acceptance Criteria

1. WHEN a check for whether a user administers a given Team is performed, THE Team_Model SHALL treat that user as a Team_Admin of the given Team if they hold a direct `team_memberships` row with `role = 'admin'` for the given Team itself, OR for any Team in the given Team's Ancestor_Chain.
2. THE Team_Model SHALL compute inherited Team_Admin status at check time by walking the given Team's Ancestor_Chain, and SHALL NOT rely on any materialized or persisted representation of inherited admin status.
3. THE Team_Model SHALL implement the behaviour described in Criteria 1 and 2 inside its existing admin-check function (`isAdmin`), such that every existing caller of that function receives inherited admin behaviour without any change to that caller's own code.
4. THE Team_Model's inherited Team_Admin behaviour SHALL be independent of, and SHALL NOT modify, the existing upward membership-inheritance mechanism represented by `team_memberships.inherited_from_team_id`.
5. WHEN a user holds a direct `role = 'admin'` `team_memberships` row for a Team with descendants, THE Client's Team Admins tab for each descendant Team SHALL display that user as an admin of the descendant Team, attributed to the ancestor Team from which their admin status is inherited.

### Requirement 5: Callsign Level Selection

**User Story:** As a Global_Manager, I want to choose which specific levels of an Organisation's Team hierarchy contribute to generated callsigns, so that I can produce callsigns with a subset of levels (for example, only the first and last configured level) rather than always the first N contiguous levels.

#### Acceptance Criteria

1. WHEN a Global_Manager creates or updates an Organisation, THE Team_Management_API SHALL accept a Callsign_Level_Selection value expressed as a set of Team_Depth positions between 1 and Max_Team_Depth inclusive. Team_Depth 0 (the Organisation itself) SHALL NOT be a member of the Callsign_Level_Selection value accepted or stored here, since Requirement 8 always includes the Organisation's own prefix regardless of Callsign_Level_Selection.
2. IF a Callsign_Level_Selection value includes a Team_Depth position outside the 1-to-Max_Team_Depth inclusive range, THEN THE Team_Management_API SHALL reject the request with a 400 response and SHALL NOT apply the change.
3. WHEN an Organisation is created without an explicit Callsign_Level_Selection value, THE Team_Management_API SHALL default that Organisation's Callsign_Level_Selection to every Team_Depth position from 1 to Max_Team_Depth inclusive.
4. WHEN the Callsign_Generator computes a callsign for a user, THE Callsign_Generator SHALL include the `callsign_prefix` of each Team in that user's Ancestor_Chain whose Team_Depth position is a member of that user's Organisation's Callsign_Level_Selection, in ascending Team_Depth order, assembled into the final callsign per Requirement 8.
5. IF a Team_Depth position in a user's Organisation's Callsign_Level_Selection has no corresponding Team in that user's Ancestor_Chain (because that user's branch of the hierarchy is shallower than the selected position), THEN THE Callsign_Generator SHALL omit that position from the generated callsign without producing an error.
6. THE Team_Management_API SHALL reject any attempt to set or update a Callsign_Level_Selection value on a Sub_Team (a Team whose `parent_team_id` is not `NULL`) with a 400 response.
7. THE Client SHALL render, on an Organisation's edit and creation views, one selectable toggle per Team_Depth position from 1 to Max_Team_Depth inclusive, for setting that Organisation's Callsign_Level_Selection, and SHALL NOT render a toggle for Team_Depth 0 (the Organisation's own prefix is never optional; see Requirement 8).
8. Multiple, differently-prefixed Sub_Teams of the Organisation MAY occupy the same Team_Depth position across different branches of the hierarchy (for example, "CB", "AUK", and "WGN" all at Team_Depth 1 under a single Organisation) -- Criteria 9-11 govern how the Client labels that position's toggle in every case, superseding any labelling scheme that would assume at most one Sub_Team per Team_Depth position.
9. THE Client SHALL always label a Team_Depth position's toggle with a "Level N" prefix, where N is that Team_Depth position, regardless of how many Sub_Teams occupy that position.
10. WHERE at least one existing Sub_Team of the Organisation occupies a given Team_Depth position, THE Client SHALL append to that position's "Level N" label a parenthetical, comma-separated list of up to 3 distinct `callsign_prefix` values drawn from Sub_Teams occupying that position (for example, "Level 1 (e.g. CB, AUK, WGN)"), and, WHERE more than 3 distinct `callsign_prefix` values occupy that position, SHALL append an ellipsis after the third listed value to indicate additional values exist beyond those shown (for example, "Level 1 (e.g. CB, AUK, WGN, ...)").
11. WHERE no existing Sub_Team of the Organisation occupies a given Team_Depth position, THE Client SHALL render that position's toggle with only the "Level N" label described in Criterion 9, with no parenthetical.
12. WHEN a Global_Manager changes an Organisation's Callsign_Level_Selection, THE Team_Management_API SHALL regenerate the Organisation segment and Team segment of every affected user's callsign (per Requirement 8), consistent with the existing behaviour of regenerating callsign attributes when `callsign_subteam_depth` changes. THE Team_Management_API SHALL NOT regenerate or alter any user's Callsign_Suffix as part of this regeneration, per Requirement 11.

### Requirement 6: Organisation-Scoped and Private-Branch-Cascading Visibility

**User Story:** As a member of an Organisation, I want to see every public Team in my own Organisation but never another Organisation's existence, and as a Global_Manager I want a private Team's entire branch (including its own Sub_Teams, regardless of their own visibility setting) hidden from anyone outside that branch, so that compartmented Teams such as a special-operations or narcotics-enforcement unit stay hidden from the rest of the Organisation.

#### Acceptance Criteria

1. WHEN a non-Global_Manager user requests a Team's details, hierarchy, sub-team list, or member/admin list, THE Team_Management_API SHALL reject the request UNLESS the requested Team is a Visible_Branch for that user.
2. IF a non-Global_Manager user requests a Team belonging to an Organisation other than their own, THEN THE Team_Management_API SHALL respond as though that Team does not exist (a 404 response), regardless of that Team's `visibility` value.
3. IF a non-Global_Manager, non-member, non-Team_Admin user requests a Team that is not a Visible_Branch for them because a private Team exists in its Ancestor_Chain, THEN THE Team_Management_API SHALL respond as though that Team does not exist (a 404 response), regardless of that Team's own `visibility` value.
4. A Global_Manager SHALL be able to view every Team's details, hierarchy, sub-team list, and member/admin list, in every Organisation, regardless of `visibility`, with no restriction imposed by this requirement.
5. WHEN an Org_Member requests the list of Teams in their own Organisation, THE Team_Management_API SHALL return every Team that is a Visible_Branch for that Org_Member, including public Teams they are not a member of, and SHALL exclude every Team that is not a Visible_Branch for them.
6. THE Client SHALL provide an Org_Member with a means of browsing every Visible_Branch Team within their own Organisation, not only the Teams they directly belong to.
7. WHEN a Global_Manager updates a Team's `visibility` to `private`, THE App SHALL apply the resulting Visible_Branch restriction to that Team and to every existing Sub_Team beneath it immediately, without requiring any change to those Sub_Teams' own `visibility` values.
8. WHEN a Team's `visibility` is `public` but an ancestor Team's `visibility` is `private`, THE App SHALL treat that Team identically to a Team whose own `visibility` is `private`, for every purpose described in this requirement.

### Requirement 7: No Join Requests Beneath a Private Team

**User Story:** As a Global_Manager, I want a private Team's entire branch to be unreachable through the public team-access-request flow, so that a compartmented Team cannot be discovered or requested by someone outside it.

#### Acceptance Criteria

1. WHEN the public, unauthenticated team-access-request flow lists joinable Teams, THE Team_Management_API SHALL exclude a Team whose `visibility` is `private`.
2. WHEN the public, unauthenticated team-access-request flow lists joinable Teams, THE Team_Management_API SHALL exclude a Team whose Ancestor_Chain contains a Team whose `visibility` is `private`, even if the Team itself has `visibility` set to `public`.
3. THE public, unauthenticated team-access-request flow SHALL continue to list joinable Teams across every Organisation, unchanged by Requirement 6 (which restricts visibility only for authenticated, already-provisioned users).
4. IF a team-access-request is submitted naming a Team that is excluded per Criteria 1 or 2, THEN THE Team_Management_API SHALL reject the request, consistent with its existing rejection of a request naming a Team that is not joinable.

### Requirement 8: Callsign Assembly Format

**User Story:** As a Global_Manager, I want an Organisation's own callsign prefix to stay visually distinct from its Team levels' prefixes, with the Team levels themselves concatenated into a single compact block, and the person's own Callsign_Suffix always last, so that a callsign like "FENZ-CBST40-J.Doe" clearly separates the Organisation from the unit path and from the person's identifier.

#### Acceptance Criteria

1. THE Callsign_Generator SHALL assemble a generated callsign from up to three segments, in this order: an Organisation segment, a Team segment, and a Name segment.
2. THE Callsign_Generator SHALL set the Organisation segment to the Organisation's own `callsign_prefix` value whenever that value is non-empty, UNCONDITIONALLY -- an Organisation's own prefix SHALL always be included in every callsign generated for any user in that Organisation's hierarchy, and there SHALL be no configuration, including Callsign_Level_Selection, that excludes it.
3. THE Callsign_Generator SHALL set the Team segment to the concatenation, in ascending Team_Depth order and with no separator between them, of every non-empty `callsign_prefix` belonging to a Team at Team_Depth 1 or greater whose Team_Depth position is a member of the Callsign_Level_Selection.
4. THE Callsign_Generator SHALL set the Name segment to that user's stored Callsign_Suffix value (Requirement 11), unconditionally -- the Name segment is never computed live from a user's name or from `callsign_name_format` at callsign-generation time.
5. THE Callsign_Generator SHALL join the Organisation segment, the Team segment, and the Name segment with a single `-` character between each pair of segments that are both non-empty, and SHALL omit a segment, and the `-` character that would otherwise separate it from an adjacent segment, when that segment is empty (for example, an Organisation with no `callsign_prefix` produces a callsign consisting of only the Team segment and Name segment joined by a single `-`, with no leading `-` and no empty leading segment).
6. THE App SHALL support a fourth `callsign_name_format` value, in addition to the three existing values (`full_name`, `first_initial_last`, `first_last_initial`), that computes a Callsign_Suffix default (per Requirement 11) as a user's first initial, immediately followed by a `.` character with no space, immediately followed by their last name (for example, "J.Doe" for a user named "John Doe").
7. THE Team_Management_API SHALL accept the `callsign_name_format` value described in Criterion 6 anywhere it currently accepts `full_name`, `first_initial_last`, or `first_last_initial`, with the same Organisation-only, inherited-by-Sub_Team behaviour specified in Requirement 3, and with the same default-computation-rule-only (never read at callsign-generation time) behaviour specified in Requirement 3 Criterion 4.

### Requirement 9: CSV Import of a Multi-Level Team Hierarchy

**User Story:** As a Global_Manager, I want to import an entire Organisation's Team hierarchy from a single CSV file, so that I do not have to manually create every Team in a large existing hierarchy such as FENZ's regions, districts, and stations one at a time through the Client.

#### Acceptance Criteria

1. THE Team_Import_Row format SHALL accept an optional `rowId` column, an import-local identifier that other Team_Import_Rows in the same file may reference as that row's parent.
2. IF a non-empty `rowId` value appears on more than one Team_Import_Row within the same file, THEN THE Team_Management_API SHALL reject the ENTIRE import, before creating any Team from that file, with an error identifying the duplicated `rowId` value; a duplicated `rowId` is not resolvable to a single parent by any rule, so it is rejected up front rather than resolved ambiguously or arbitrarily.
3. THE Team_Import_Row format SHALL accept an optional `parentRowRef` column, whose value, when present, SHALL match another Team_Import_Row's `rowId` value within the same file, identifying that row's parent Team.
4. IF a Team_Import_Row's `parentRowRef` value does not match any `rowId` value present in the same file, THEN THE Team_Management_API SHALL reject that row with an error identifying the unmatched `parentRowRef` value, and SHALL NOT create a Team for that row.
5. THE Team_Import_Row format SHALL continue to accept the existing `parentTeamName`/`parentTeamId` columns, for referencing a parent Team that already exists in the database rather than another row in the same file. WHEN a Team_Import_Row supplies both a `parentRowRef` and a `parentTeamName`/`parentTeamId`, THE Team_Management_API SHALL reject that row with an error stating that only one parent-reference method may be used per row.
6. THE Team_Management_API SHALL resolve every Team_Import_Row's parent (whether by `parentRowRef`, `parentTeamName`, or `parentTeamId`) before creating any Team from that file, such that the order in which rows appear in the file does not affect the outcome of the import.
7. THE Team_Import_Row format SHALL accept an optional `visibility` column, accepting the same values the Team_Management_API accepts when creating a Team directly. WHEN a Team_Import_Row omits `visibility`, THE Team_Management_API SHALL default that row's Team to `public`, consistent with THE Team_Management_API's existing default when creating a Team directly through its non-CSV endpoint.
8. THE Team_Import_Row format SHALL accept an optional `callsignPrefix` column, populating that row's Team's `callsign_prefix` value.
9. WHEN a Team_Import_Row would create a Team at a Team_Depth greater than Max_Team_Depth, THE Team_Management_API SHALL reject that row with an error stating Max_Team_Depth, and SHALL NOT create a Team for that row, consistent with Requirement 2's enforcement for a non-CSV Team creation request.
10. WHEN a Team_Import_Row creates a Sub_Team (a row whose parent, however resolved, is not a root Team), THE Team_Management_API SHALL set that Sub_Team's `color` and `callsign_name_format` to its Organisation's current `color` and `callsign_name_format` values, consistent with Requirement 3's enforcement for a non-CSV Sub_Team creation request.
11. WHEN a Team_Import_Row creates a root Team (an Organisation), THE Team_Import_Row format SHALL accept optional `color` and `callsignNameFormat` columns for that row, consistent with the values accepted when creating an Organisation directly through its non-CSV endpoint.
12. IF a Team_Import_Row's parent (however resolved) has not yet been successfully created within the same import (for example, because an earlier row referencing it as `parentRowRef` failed per Criterion 4), THEN THE Team_Management_API SHALL reject that row, rather than creating a Sub_Team with no valid parent.
13. IF two or more Team_Import_Rows' `parentRowRef` values form a cycle (directly, as in Row A referencing Row B as parent and Row B referencing Row A as parent, or indirectly through a longer chain, e.g. A -> B -> C -> A), THEN THE Team_Management_API SHALL detect that cycle before creating any Team from that file, and SHALL reject the ENTIRE import with an error identifying every Team_Import_Row participating in the cycle, rather than rejecting cycle members one at a time as unresolvable parents per Criterion 12 (which alone would never terminate for a cycle, since every member of a cycle is always waiting on another member of the same cycle).
14. THE downloadable Team CSV import template (`public/templates/team-import-template.csv`) SHALL be updated to include and demonstrate the `rowId`, `parentRowRef`, `visibility`, and `callsignPrefix` columns, using an example hierarchy at least three Team_Depth levels deep.

### Requirement 11: Per-User Callsign Suffix, Defaulted by Organisation Format and Always Admin-Editable

**User Story:** As a Global_Manager, I want every user to have a single, always-editable Callsign_Suffix that starts from a sensible default based on my Organisation's chosen format, and I want the App to prevent two members of the same Team from ever ending up with the same Callsign_Suffix, so that a collision (for example, two people both named John/James Doe defaulting to the same "J.Doe") is caught and blocked at the moment it would occur rather than silently producing two operationally indistinguishable callsigns on the same roster, and so that an Organisation that identifies personnel by badge number can use that instead of a name at all.

#### Acceptance Criteria

1. THE `users` table SHALL gain a `callsign_suffix` column, present for every user regardless of Organisation.
2. THE Callsign_Generator SHALL set the Name segment of every generated callsign (per Requirement 8 Criterion 4) to that user's stored `callsign_suffix` value, for every user in every Organisation, regardless of that Organisation's `callsign_name_format` value.
3. THE Team_Management_API SHALL accept a `callsign_suffix` value only if it is empty, or consists exclusively of letters (A-Z, case-insensitive), digits (0-9), the `-` character, and the `.` character. This is deliberately broader than `callsign_prefix` (Requirement 3 Criteria 8-9), which permits neither `-` nor `.`: a `callsign_suffix` value occupies the Name segment, the LAST segment in callsign assembly (Requirement 8 Criterion 1), with nothing after it to be confused with -- so a `-` or `.` inside it cannot be mistaken for a segment boundary the way either character could if it appeared inside a `callsign_prefix` value (which participates in the Team segment's no-separator concatenation, Requirement 8 Criterion 3, or in the `-`-joined segment assembly at Team_Depth 0, Requirement 8 Criterion 5). `callsign_suffix` permits `.` specifically so the format described in Requirement 8 Criterion 6 (e.g. "J.Doe") can be stored with its period intact.
4. A user's `callsign_suffix` value SHALL be settable and updatable only by a Team_Admin (of any Team in that user's Ancestor_Chain, per Requirement 4's inherited admin status) or a Global_Manager. THE Client SHALL render `callsign_suffix` as read-only to the user it belongs to, and as editable to a Team_Admin or Global_Manager managing that user.
5. THE App SHALL support a fifth `callsign_name_format` value, `user_defined`, in addition to the four values described elsewhere in this document (`full_name`, `first_initial_last`, `first_last_initial`, and the value described in Requirement 8 Criterion 6). `user_defined` computes no default value at all (Criterion 7 does not apply when an Organisation's `callsign_name_format` is `user_defined`).
6. WHEN a Team_Admin or Global_Manager creates a new user within an Organisation whose `callsign_name_format` is `user_defined`, THE Team_Management_API SHALL require a non-empty `callsign_suffix` value to be supplied for that user at creation time, and SHALL reject the creation request with a 400 response if one is not supplied, consistent with the existing requirement to supply that user's email address.
7. WHEN a Team_Admin or Global_Manager creates a new user within an Organisation whose `callsign_name_format` is NOT `user_defined`, THE Team_Management_API SHALL compute a default `callsign_suffix` value for that user from that user's name, using that Organisation's `callsign_name_format` value as the computation rule (`full_name`, `first_initial_last`, `first_last_initial`, or the format described in Requirement 8 Criterion 6), with every character other than a letter, digit, `-`, or `.` replaced by a single `-` (a `.` produced by the format described in Requirement 8 Criterion 6 is therefore preserved, not replaced), and SHALL store that computed value as the new user's `callsign_suffix` unless the creating Team_Admin or Global_Manager supplies a different `callsign_suffix` value in the same request, in which case the supplied value SHALL be stored instead.
8. Once a user's `callsign_suffix` has been set (whether by the default computation described in Criterion 7, by an explicit value supplied at creation, or by a subsequent edit), THE App SHALL NOT recompute or otherwise modify that value as a side effect of any other change, including but not limited to: a correction to that user's first or last name; a change to that user's Organisation's `callsign_name_format` value; or that user being moved from one Organisation, or one Team, to another. A `callsign_suffix` value changes only as the direct result of a Team_Admin or Global_Manager explicitly editing it.
9. WHEN the public, unauthenticated team-access-request flow is used to request access to a Team whose Organisation's `callsign_name_format` is `user_defined`, THE Client SHALL prompt the requester for a `callsign_suffix` value as part of that request, and THE Team_Management_API SHALL store it with the resulting access request.
10. WHEN the public, unauthenticated team-access-request flow is used to request access to a Team whose Organisation's `callsign_name_format` is NOT `user_defined`, THE Client SHALL NOT prompt the requester for a `callsign_suffix` value.
11. WHEN a Team_Admin or Global_Manager reviews a pending access request naming a Team whose Organisation's `callsign_name_format` is NOT `user_defined`, THE Client SHALL display the `callsign_suffix` default value that would be computed for that requester per Criterion 7, and SHALL allow the reviewer to change it before approving the request; THE Team_Management_API SHALL store whichever value (the computed default, or the reviewer's edited value) is in effect at the moment the request is approved as the new user's `callsign_suffix`.
12. WHEN a Team_Admin or Global_Manager approves a pending access request that supplied a `callsign_suffix` value per Criterion 9, THE Client SHALL display that supplied value and SHALL allow the reviewer to change it before approving, mirroring Criterion 11's review behaviour.
13. THE Client SHALL provide a `callsign_suffix` input control, enforcing the character restriction described in Criterion 3 at the point of entry, on every view where a Team_Admin or Global_Manager creates or edits a user, or reviews a pending access request, per Criteria 6, 7, 11, and 12.
14. THE Team_Management_API SHALL reject a non-empty `callsign_suffix` value, whether supplied explicitly or computed as a default per Criterion 7, with a 400 response identifying the conflicting user, if a case-insensitive match of that value already exists as another user's `callsign_suffix` among that Team's Member_List (every direct and inherited member and admin of the Team the `callsign_suffix` is being set for, per Requirement 13's existing Member_List definition). An empty `callsign_suffix` value is exempt from this check.
15. WHEN the default `callsign_suffix` computed per Criterion 7 would conflict per Criterion 14 (for example, two users named John Doe and James Doe on the same Team both defaulting to "J.Doe"), THE Team_Management_API SHALL reject the user-creation request rather than silently storing a colliding value, requiring the creating Team_Admin or Global_Manager to supply a non-conflicting `callsign_suffix` explicitly in the same request.
16. WHEN a Team_Admin or Global_Manager attempts to edit an existing user's `callsign_suffix` to a value that conflicts per Criterion 14, THE Team_Management_API SHALL reject the edit and SHALL NOT change that user's stored `callsign_suffix`.
17. WHEN a Team_Admin or Global_Manager attempts to approve a pending access request whose effective `callsign_suffix` (per Criteria 9, 11, or 12) conflicts per Criterion 14 against the target Team's existing Member_List, THE Team_Management_API SHALL reject the approval, and THE Client SHALL surface the conflicting value to the reviewer so they can supply a different one before retrying the approval.
18. IF a user's Team membership changes such that they become a direct or inherited member of a Team whose existing Member_List already contains that user's current `callsign_suffix` value on another user, THEN THE Team_Management_API SHALL reject that membership change, consistent with Criterion 14's per-Team uniqueness rule; a Team_Admin or Global_Manager MAY first change one of the two conflicting `callsign_suffix` values (subject to Criterion 16) and then retry the membership change.

### Requirement 13: Member List Display and Editing

**User Story:** As a Team_Admin or Global_Manager viewing a Team's or Organisation's Member_List, I want to see each member's full name, email, and TAK_Role, and edit the name and TAK_Role directly from that list, so that I can correct a member's details without navigating away, while their email (their primary identifier) stays protected from accidental change.

#### Acceptance Criteria

1. THE Client SHALL display, for every member and admin shown in a Member_List, that member's full name, email address, and TAK_Role.
2. THE Client SHALL allow a Team_Admin or Global_Manager to edit a Member_List member's first name, last name, and TAK_Role directly from the Member_List.
3. THE Client SHALL NOT provide any control to edit a Member_List member's email address from the Member_List or from any editing view reachable from it. THE Team_Management_API SHALL reject any request that attempts to change a user's email address through the editing capability described in this requirement.
4. THE Team_Management_API SHALL accept a TAK_Role value only if it is one of the eight predefined values (Team Member, Team Lead, Sniper, Medic, Forward Observer, RTO, K9, HQ), consistent with the existing Role Descriptions configuration surface, and SHALL reject a request supplying any other value with a 400 response.
5. THE Client SHALL present the TAK_Role editing control as a selection among the eight predefined values described in Criterion 4, not as free-text entry.
6. WHEN a Team_Admin or Global_Manager edits a Member_List member's TAK_Role, THE App SHALL update that user's `tak_role` value in the local database and SHALL update the corresponding `takRole` attribute on that user's Authentik account, consistent with the existing pattern used for other TAK attribute updates (`UserAttributesService.updateUserAttributes`).
7. A new user SHALL default to a TAK_Role of "Team Member" at creation time.
8. Once a user's TAK_Role has been established (whether by the default described in Criterion 7 or by a subsequent edit), THE App SHALL NOT recompute or otherwise modify that value as a side effect of any other change, including but not limited to: a correction to that user's first or last name; that user being moved from one Team, or one Organisation, to another; or any Callsign_Suffix, Callsign_Level_Selection, or callsign-attribute regeneration described elsewhere in this document. A TAK_Role value changes only as the direct result of a Team_Admin or Global_Manager explicitly editing it via the capability described in this requirement.
9. WHEN a Team_Admin or Global_Manager edits a Member_List member's first name or last name, THE App SHALL update that user's `first_name`/`last_name` values in the local database, consistent with the existing effect of the self-service name-change request-and-approval flow, but without requiring that flow's request-and-approval steps when performed by a Team_Admin or Global_Manager directly from the Member_List.
10. THE Member_List SHALL be subject to the same Visible_Branch restriction described in Requirement 6: a Team_Admin or Global_Manager may edit a member's name or TAK_Role only for a Team that is a Visible_Branch for them (or, for a Global_Manager, any Team).

### Requirement 14: Complete, Working Client Functionality for Every Requirement in This Document

**User Story:** As a user of the Client, I want every capability described in this document to be fully usable end-to-end through the Client's own pages and controls, so that I never encounter a button that throws an unhandled 4xx/5xx error, a form whose submission silently fails to persist, or a capability that exists only as an API with no Client entry point at all.

#### Acceptance Criteria

1. FOR every capability described in Requirements 1-9, 11, and 13 that a Global_Manager, Team_Admin, or Org_Member can invoke, THE Client SHALL provide a corresponding page, dialog, or control through which that capability can be invoked, without requiring direct use of the Team_Management_API.
2. WHEN a Client control invokes an API request described in Requirements 1-9, 11, or 13, THE Client SHALL handle both a successful response and an error response (4xx or 5xx) from that request, and SHALL present a user-visible indication of failure rather than allowing an unhandled error to surface in the browser console with no visible feedback.
3. WHEN a Client form submission described in Requirements 1-9, 11, or 13 succeeds, THE Client SHALL reflect the saved values in its own subsequently rendered state (whether by re-fetching from the Team_Management_API or by updating local state from that request's own response), such that a user is never shown a value that was not actually persisted.
4. THE verification process for this feature SHALL include exercising every new or changed Client control described in Requirements 1-9, 11, and 13 against a running instance of the App (not solely automated tests of the Team_Management_API in isolation), to confirm each control functions end-to-end before this feature is considered complete.
