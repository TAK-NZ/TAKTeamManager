# Requirements Document

## Introduction

This feature adds an optional TAK device-management capability to TAK Team Manager: visibility into the TAK Server client certificates ("devices") a user holds, a best-effort "last seen" indicator for each device, and the ability to revoke a device's certificates. It is modeled on the analysis in `tak-infra/DEVICE_LAST_SEEN_TRACKING.md`, with one deliberate divergence: last-seen data is derived ONLY from TAK Server's own Marti HTTP API, NOT from a direct `cot_router` Postgres query. There is therefore no direct TAK Server database access, no new database role, and no `cot_router` query anywhere in this feature.

### Revision note: empirically corrected endpoint contract

The first implementation of this feature was written against assumptions about TAK Server's certificate and client APIs that were never checked against a running server. They were subsequently checked, against the live TAK Server with the Admin_Credential, and several of them were false. The authoritative endpoint contract for this feature is TAK Server's own OpenAPI 3.1 document, committed at `tak-server-openapispec.json` (308 paths); every endpoint this document names is cited from it, and an endpoint absent from it is treated as non-existent.

The corrections, in brief (the numbers behind them are recorded in `design.md`'s "Findings that invalidated earlier assumptions"):

1. **`/Marti/clients` does not exist.** It answers 404 and is absent from the OpenAPI document entirely. The implemented `getConnectedSubscriptions()` called it, and Requirement 3.8's graceful-404-as-empty handling turned that 404 into "no clients observed" — so Last_Seen stayed null forever and no error was ever raised. Corrected in 3.1, 3.2, 3.8, in the Subscriptions_API glossary entry, and generalized in Requirement 14.
2. **`GET /Marti/api/certadmin/cert/active` is not "non-revoked, non-superseded".** It returned 95 certificates, 90 of which also appear in `GET /Marti/api/certadmin/cert/revoked`. Corrected in 4.3, 4.6 and the Active_Certificate glossary entry, and specified in Requirement 11.
3. **`revocationDate` is not a revocation signal.** All 95 certificates in `/active` carry a non-null `revocationDate`, including the 5 that TAK Server does NOT list under `/revoked`. Membership in `/revoked` is the authoritative signal. Corrected in 7.6, 8.7 and specified in Requirement 12.
4. **`GET /Marti/api/certadmin/cert/replaced` cannot exclude superseded certificates** — it returned the same 95 ids as `/active`. Superseding is computed locally (newest `issuanceDate` per `clientUid`). Corrected in 4.6 and specified in Requirement 11.
5. **`clientUid` is heavily reused** — 95 certificates collapse to 10 distinct `clientUid`s. A Device is a `clientUid` with a SET of certificates, not one certificate. Corrected in 4.4, 4.5 and the Device glossary entry; specified in Requirement 11.
6. **Revocation was over-scoped.** The enqueued payload is `{ tak_usernames: [username] }`, and the handler matches every certificate whose `creatorDn` matches that username — so revoking one device revoked every certificate that user held across all their devices. Corrected in 7.4, 8.4 and specified in Requirement 12.
7. **Last_Seen has a real source**: `GET /Marti/api/clientEndPoints` returns TAK Server's own last-seen history (`ClientEndpoint.lastEventTime`), keyed by `uid` in the same space as our `client_uid`. Corrected in 3.1, 3.2, 3.7 and specified in Requirement 13.

The feature is gated behind a single server-side environment flag, `DEVICE_MGMT_ENABLED`, defaulting to `false`. WHILE the flag is disabled the feature is entirely inert: no admin credential is loaded, no polling or sync runs, no new route or user-interface surface is reachable, and no revocation can be initiated. The flag is read only on the server, following the existing `CLOUDTAK_ENABLED` / `isCloudTakEnabled()` pattern in `server/config/cloudtak.js`.

The feature reuses existing building blocks rather than introducing new frameworks: the secrets-provider abstraction (`server/config/secretsProvider.js`) for loading the TAK Server admin credential; `TakServerService` (`server/services/TakServerService.js`) and its mutual-TLS agent construction, `findCertificatesForUser`, and `matchesCreatorDn` for talking to the Marti `certadmin` API; the Sync_Worker scheduled-job pattern (`ExpiryScheduler`, `RetentionCleanupJob` running on their own 24-hour/interval timers inside `server/workers/syncWorker.js`) for the credential refresh and the device poller; the durable `sync_operations` queue via `EventPublisher.publishOperation` and the existing `revoke_tak_certificates` operation handler for revocation; and the existing direct-admin managed-user scoping (`role = 'admin'` AND direct membership; `DirectoryScopeService`) for admin visibility. This feature also consolidates the single existing consumer of the TAK admin credential — the Sync_Worker's `revoke_tak_certificates` handler via `TakServerService` — onto the same shared, refreshable credential loader, so both revocation and device-management use one credential mechanism and pick up rotations without a restart. The credential can be loaded from a Secrets Manager PKCS#12 bundle (stored as `SecretBinary`), with the existing file/environment path retained as a fallback. Device data is persisted in a new local Postgres table in TAK Team Manager's own database via a `node-pg-migrate` incremental migration.

This document specifies only the behavior of this feature. It does not restate the existing Sync_Worker, `EventPublisher`, `TakServerService`, secrets-provider, or authorization behavior it builds on, except where a new requirement constrains that behavior.

## Glossary

- **Device_Management**: The optional feature specified by this document that surfaces a user's TAK Server device certificates, a best-effort Last_Seen indicator, and certificate revocation.
- **Device_Mgmt_Enabled**: The server-side boolean derived from the `DEVICE_MGMT_ENABLED` environment variable, true only when `process.env.DEVICE_MGMT_ENABLED === 'true'`, and false when the variable is unset or holds any other value. Read on the server only. Exposed through `isDeviceMgmtEnabled()` in a new `server/config/deviceMgmt.js`, analogous to `isCloudTakEnabled()` in `server/config/cloudtak.js`.
- **Device**: One TAK Server client identified by a single `clientUid`, together with the SET of Live_Certificates issued for that `clientUid`, and a Last_Seen value. A Device is NOT one certificate: `clientUid` is heavily reused across re-enrollments, so a single Device commonly holds many certificates (verified live: 95 certificates collapsed to 10 distinct `clientUid`s, with 60 certificates on one of them). A Device's displayed certificate attributes (certificate id, issuance date, expiration date) come from the Newest_Live_Certificate. See Requirement 11.
- **Active_Certificate**: A certificate as returned by `GET /Marti/api/certadmin/cert/active` (OpenAPI `getActive`, `ApiResponseListTakCert`). This view is NOT the set of non-revoked, non-superseded certificates: verified live, it returned 95 certificates of which 90 also appear in Revoked_Certificate_View, and `GET /Marti/api/certadmin/cert/replaced` returned that same 95-id set. It is therefore only the *candidate* set that Live_Certificates are computed from, never the live set itself.
- **Revoked_Certificate_View**: The set returned by `GET /Marti/api/certadmin/cert/revoked` (OpenAPI `getRevoked`, `ApiResponseListTakCert`). Membership in this view is the ONLY authoritative revocation signal for a certificate. A certificate's `revocationDate` field is NOT a revocation signal: verified live, every one of the 95 certificates in the Active_Certificate view carried a non-null `revocationDate`, including the 5 that TAK Server does not list here.
- **Live_Certificate**: A certificate that is present in the Active_Certificate view AND absent from the Revoked_Certificate_View. A Device's Live_Certificates are the Live_Certificates carrying its `clientUid`. Applying this definition plus Newest_Live_Certificate to the live server yielded exactly 1 live Device UID out of the 10 the earlier implementation listed.
- **Newest_Live_Certificate**: The Live_Certificate with the greatest `issuanceDate` among a Device's Live_Certificates. Superseding is computed locally this way because TAK Server exposes no usable superseded view (`/Marti/api/certadmin/cert/replaced` returns the same set as `/active`).
- **Client_Uid**: The `clientUid` field of a TAK certificate (OpenAPI `TakCert.clientUid`), used as the stable Device identifier and as the primary key of the Device_Table. It is shared by every certificate issued for the same client, so it identifies a Device rather than an enrollment.
- **Client_Type**: The client platform a Device runs, derived server-side as a pure function of Client_Uid alone: CloudTAK, Android/ATAK, iOS/iTAK, Windows/WinTAK, or Unknown. Exposed as a `clientType` field on the Device wire shape and rendered as a Device_Type_Icon. See Requirement 15.
- **Device_Type_Icon**: The small inline-SVG glyph representing a Device's Client_Type, rendered by a single shared `DeviceTypeIcon` client component so the Dashboard card and the user-details modal cannot diverge.
- **Icon_Only_Action**: A list row action rendered as an icon rather than a text label, carrying an `aria-label` accessible name and a tooltip that appears on hover AND on keyboard focus. The general list-action convention for this codebase; the Revoke action is one. See Requirement 16.
- **Last_Seen**: A nullable timestamp for a Device, taken from TAK Server's own last-seen history: the `lastEventTime` of the Client_Endpoints_API entry whose `uid` equals the Device's Client_Uid. It is best-effort in that TAK Server may retain no entry for a Device (in which case Last_Seen stays null and is presented as "never seen"), but it is TAK Server's recorded history rather than a reconstruction from snapshots.
- **Client_Endpoints_API**: `GET /Marti/api/clientEndPoints` (OpenAPI `getClientEndpoints`, `ApiResponseListClientEndpoint`, schema `ClientEndpoint { callsign, uid, username, team, role, lastEventTime (date-time), lastStatus }`, query parameters `secAgo`, `showCurrentlyConnectedClients`, `showMostRecentOnly`, `group`). TAK Server's own per-client last-seen history, including disconnected clients. Verified live: 48 entries, 46 `lastStatus: "Disconnected"` carrying timestamps and 2 `"Connected"`, with `uid` values in the same space as our `client_uid` (e.g. `ANDROID-842f08e120efdbe3`). Two of its fields are consumed: `lastEventTime` as the Last_Seen source (Requirement 13) and `lastStatus` as the Connection_Status source (Requirement 20). A UID may appear in SEVERAL entries with differing `lastStatus` (verified live: one Windows SID returned four entries under different callsigns), which is why Connection_Status needs the Status_Collapse_Rule rather than a single lookup.
- **Subscriptions_API**: Retained as an alias of the Client_Endpoints_API, so the criteria and tests that already cite this term keep their meaning. Its earlier definition — the live connected-clients snapshot at `/Marti/clients`, backed by `SubscriptionApi.getAllSubscriptions()` — was wrong in two ways: `/Marti/clients` does not exist on TAK Server (404, and absent from the OpenAPI document entirely), and the endpoint that does exist for live subscriptions, `GET /Marti/api/subscriptions/all` (`ApiResponseSetSubscriptionInfo`), is not a usable key source for this feature because its `clientUid` was empty in 14 of 16 live entries. Wherever this document says Subscriptions_API, read Client_Endpoints_API.
- **Subscription_Poller**: The scheduled job, running inside the Sync_Worker process on its own timer, that reads the Client_Endpoints_API each run and records, for each matching Device, its Last_Seen from the reported `lastEventTime` subject to the Monotonic_Guard, AND its Connection_Status from the reported `lastStatus` NOT subject to the Monotonic_Guard (Requirement 20.3). **Amended in place (Requirement 20):** this entry previously described the Last_Seen write as the poller's only write, which is no longer the whole of what one run records.
- **Monotonic_Guard**: The constraint that a poll never moves a Device's stored Last_Seen backward and never nulls an already-set Last_Seen, applied as a SQL-level clamp. With the Client_Endpoints_API as the source this is a safety guard against a shrinking/rewound upstream history rather than the mechanism by which history is reconstructed. Requirement 9.8's fast-check property test remains required and applies to this guard. It governs `last_seen_at` ONLY: it SHALL NOT gate the Connection_Status write, because Connection_Status is current state rather than a running maximum (Requirement 20.3).
- **Admin_Credential**: The TAK Server admin x.509 client credential (P12 bundle or cert/key pair) used by `TakServerService` to authenticate to the Marti `certadmin` API over mutual TLS. It may be sourced either from a Secrets Manager PKCS#12 bundle (stored as `SecretBinary`) or from the existing file/environment path, per Credential_Source.
- **Admin_Credential_Loader**: The startup + scheduled component that loads the Admin_Credential from AWS Secrets Manager via the Secrets_Provider, caches it, and refreshes it every 24 hours so a rotated credential is picked up without a process restart.
- **Admin_Cert_Secret_Arn**: The AWS Secrets Manager secret identifier (a full ARN is accepted directly as the SDK `SecretId`) naming the PKCS#12 Admin_Credential bundle, provided via `TAK_ADMIN_CERT_SECRET_ARN` when Credential_Source is `secrets-manager`.
- **Binary_Secret_Read**: A Secrets_Provider capability that returns a secret's raw `SecretBinary` value as a Buffer (distinct from the existing string `getSecret`), required because the Admin_Credential secret is stored as `SecretBinary`, not `SecretString`.
- **Credential_Source**: The configured origin of the Admin_Credential, selected by `TAK_ADMIN_CERT_SOURCE`: `secrets-manager` (load a PKCS#12 bundle from AWS Secrets Manager) or `file` (the existing file/environment mutual-TLS path). Defaults to `file` when unset, preserving current behavior.
- **P12_Passphrase**: The passphrase used to open the PKCS#12 Admin_Credential bundle. Defaults to the well-known TAK value `atakatak` (verified to open the reference bundle) when not explicitly configured, and is overridable via `TAK_ADMIN_CERT_PASSPHRASE`. Treated as sensitive and never logged.
- **Secrets_Provider**: The existing secrets-resolution abstraction in `server/config/secretsProvider.js` (`EnvSecretsProvider` / `AwsSecretsManagerProvider`, selected by `getSecretsProvider`).
- **Mutual_TLS_Agent**: The `https.Agent` — and the agent options `buildMutualTlsAgentOptions(env)` in `server/services/TakServerService.js` produces — through which `TakServerService` presents the Admin_Credential to TAK Server and verifies TAK Server's own TLS server certificate. It is shared by the Sync_Worker's `revoke_tak_certificates` handler and the device-management jobs, per Requirement 2.8.
- **Expected_Server_Name**: The TLS server name that TAK Server's own server certificate actually carries in its subject and subjectAltName (`takserver` on a stock TAK Server deployment), which is normally NOT the DNS name operators dial. Configured via `TAK_SERVER_TLS_SERVERNAME`; WHERE it is set, it is the name the Mutual_TLS_Agent verifies TAK Server's identity against.
- **Server_Trust_Bundle**: The CA certificate bundle the Mutual_TLS_Agent verifies TAK Server's certificate chain against, supplied as the `ca` agent option from `TAK_CA_PATH`. TAK Server's chain is issued by a private TAK CA (a self-signed root), so the public root store alone cannot verify it.
- **Device_Table**: A new local Postgres table (a `tak_devices`-style table) in TAK Team Manager's own database that persists synced Device data. Columns: `client_uid` (primary key), the associated local user, TAK certificate id, certificate issued/expires timestamps, `last_seen_at` (nullable), `last_polled_at`, and a `revoked` flag.
- **Device_Sync**: The scheduled job, running inside the Sync_Worker process, that fetches the Active_Certificate view and the Revoked_Certificate_View, computes each Device's Live_Certificates and Newest_Live_Certificate, upserts one Device_Table row per Client_Uid, and deletes the Stale_Device_Rows (Requirement 17).
- **Live_Device_Set**: The set of Client_Uids one Device_Sync run derived from the Live_Certificates it fetched — exactly the Client_Uids that run upserts. A Client_Uid absent from it carries no Live_Certificate at all, either because every certificate carrying it is in the Revoked_Certificate_View or because TAK Server no longer holds any certificate for it.
- **Stale_Device_Row**: A Device_Table row whose `client_uid` is absent from the Live_Device_Set of a Device_Sync run that completed successfully. The row describes a Device that is no longer live. See Requirement 17.
- **Sync_Worker**: The durable background worker (`server/workers/syncWorker.js`) that runs the poll loop and the scheduled jobs (`ExpiryScheduler`, `RetentionCleanupJob`) on their own timers.
- **Managed_User**: A user whom an admin directly manages via the existing direct-admin relationship (`team_memberships` row with `role = 'admin'` AND `inherited_from_team_id IS NULL`), the same direct-admin concept the cloudtak-agency-groups feature uses and that `DirectoryScopeService` resolves.
- **Revoke_Confirmation_Word**: The exact literal string `REVOKE` that a user must type to confirm a revocation. It is NOT the device UID.
- **Revoke_Operation**: The existing `revoke_tak_certificates` Sync_Operation (see `server/services/TakCertificateRevocationService.js`, `TakServerService.revokeCertificates`, and the handler in `server/workers/syncWorker.js`) that Device_Management reuses to revoke a Device's Live_Certificates. Its payload must become device-scoped (see Requirement 12); the user-scoped `{ tak_usernames: [...] }` payload it carries today revokes every certificate the named user holds across all their Devices.
- **Revoke_Enabled**: The server-side boolean derived from the `DEVICE_MGMT_REVOKE_ENABLED` environment variable, true only when `process.env.DEVICE_MGMT_REVOKE_ENABLED === 'true'`, and false when the variable is unset or holds any other value. It is a SEPARATE flag from Device_Mgmt_Enabled and gates the destructive capability — issuing a revoke — independently of the read capability, so enabling device management in order to look at a device list does not also arm certificate revocation. Its default is false. Read on the server only, exposed through an `isDeviceMgmtRevokeEnabled()` function alongside `isDeviceMgmtEnabled()` in `server/config/deviceMgmt.js`, and never included in the Public_Config_Endpoint response.
- **Revoke_Dry_Run**: The mode in force WHILE Revoke_Enabled is false. The exact certificate ids that WOULD be revoked are resolved and logged as a Revoke_Audit_Record, and no `DELETE /Marti/api/certadmin/cert/revoke/{ids}` is issued. A Revoke_Operation executed in this mode completes as a dry-run rather than failing, and never flips the Device_Table `revoked` flag.
- **Revoke_Blast_Radius_Cap**: The maximum number of certificates one Revoke_Operation may target, configured via `DEVICE_MGMT_REVOKE_MAX_CERTS` with a documented default of 250. The default is chosen to exceed the largest real per-Device certificate count observed on the live server (60 certificates on `ckadmin (ETL)`) while still bounding a runaway resolution. Exceeding the cap aborts the operation; it never truncates the target set.
- **Revoke_Audit_Record**: The single pre-action log line, emitted via the Structured_Logger BEFORE any `DELETE` is issued, that names the target `client_uid`, every targeted certificate id, the resolved count, the acting user, and the Sync_Operation id. It is emitted in Revoke_Dry_Run mode as well as in live mode, so the set a revoke would have touched is recorded whether or not the revoke fires.
- **Public_Config_Endpoint**: The `GET /api/config/public` endpoint that returns client-visible configuration, assembled by `SiteConfig.getPublicConfig()` in `server/models/SiteConfig.js`.
- **Structured_Logger**: The existing logger (`server/config/logger`, `createLogger(...)`) used for all server logging, consistent with the repository's no-console lint rule for production code.
- **Presentation_Config**: The subset of Public_Config_Endpoint keys that exist only so the client can RENDER something the way an operator configured it: `display_timezone` (Requirement 18) and `device_expiry_warning_days` (Requirement 21). A Presentation_Config key carries no security meaning, arms no capability, and is useless on the server, which is what makes exposing it a different decision from exposing Device_Mgmt_Enabled or Revoke_Enabled — those two describe the arming state of a destructive capability and stay server-side (Criteria 1.4, 12.9). The existing `channel_folder_separator`, `maxTeamDepth` and `takRoleValues` keys are the precedent for this category.
- **Display_Timezone**: The IANA time-zone name that every user-visible date in the application is rendered in, configured via the `DISPLAY_TIMEZONE` environment variable and defaulting to `Pacific/Auckland`. It is a presentation setting only: no stored, logged, or API-transported timestamp changes because of it. See Requirement 18.
- **Date_Format_Helpers**: The shared `formatDate(value, fallback)` and `formatDateTime(value, fallback)` functions in `client/src/utils/dateFormat.js`, the single place the application turns an instant into the `yyyy-mm-dd` / `yyyy-mm-dd HH:MM` strings it shows a user. Every user-visible date in the application already goes through them (`components/DeviceListRow.jsx`, `components/OrgInterestRequests.jsx`, `pages/Users.jsx`, `pages/AuditLogs.jsx`, `pages/Admin.jsx`, `pages/Requests.jsx`), which is why applying the Display_Timezone inside them is app-wide by construction.
- **Display_Timezone_Fallback_Chain**: The ordered, non-throwing resolution the Date_Format_Helpers apply to arrive at a usable zone: the configured Display_Timezone, then the literal default `Pacific/Auckland`, then `UTC`. A zone the runtime does not recognise moves to the next link rather than raising, so a mistyped `DISPLAY_TIMEZONE` cannot blank out or crash every date in the application. See Criterion 18.8.
- **Device_List_Refresh_Interval**: The 60000 ms cadence at which the Dashboard "My Devices" card re-fetches its device list, matching the existing channel-data card in the same file rather than introducing a second cadence. See Requirement 19.
- **Visibility_Pause_Pattern**: The existing auto-refresh discipline in `client/src/pages/Dashboard.jsx`: a `setInterval` at Device_List_Refresh_Interval, cleared on `document.hidden` via a `visibilitychange` listener, and on becoming visible again re-fetching immediately before restarting the interval, with both the listener and the interval torn down on unmount. Requirement 19 reuses it rather than adding a parallel mechanism.
- **Connection_Status**: A Device's CURRENT connection state as TAK Server reports it — derived from the Client_Endpoints_API's `ClientEndpoint.lastStatus`, persisted on the Device_Table, and exposed as a `connected` boolean on the Device wire shape. It is current state read from TAK Server, not a property derivable from a certificate and not a running maximum, which is why it is stored and why the Monotonic_Guard must not gate its write. See Requirement 20.
- **Status_Collapse_Rule**: The rule that resolves the several Client_Endpoints_API entries a single `uid` may carry into one Connection_Status: the Device is connected WHEN at least one entry for that `uid` reports `lastStatus` equal to `Connected` (compared case-insensitively), and is not connected otherwise. A Device with one live connection is connected regardless of how many stale entries TAK Server also holds for it. See Criterion 20.5.
- **Connected_Label**: The text — not a colour, not a glyph alone — by which a currently-connected Device is presented in a device list, occupying the Last Seen cell, with the Last_Seen timestamp retained beside it when one is known. See Criterion 20.9.
- **Expiry_Warning_Days**: The number of days before a Device's `expires_at` at which that Device's Expires value begins to be rendered as an Imminent_Expiry, configured via `DEVICE_MGMT_EXPIRY_WARNING_DAYS` and defaulting to 30. See Requirement 21.
- **Imminent_Expiry**: The state of a Device whose `expires_at` is a known instant that is not in the past and falls within Expiry_Warning_Days of now. Rendered bold and red WITH the text marker required by Criterion 21.3.
- **Expired_Certificate_State**: The state of a Device whose `expires_at` is a known instant already in the past. It shares Imminent_Expiry's bold-red treatment but carries a DIFFERENT text marker, because "expires soon" is a false statement about a date that has passed and the two states call for different action. See Criteria 21.5, 21.6.
- **CloudTAK_Connection_Prefix**: The literal string `ANDROID-CloudTAK-` that upstream CloudTAK prepends to a user's account identifier when it builds the CoT/connection UID for a CloudTAK session (`api/common/connection-config.ts:170` in `/home/ubuntu/GitHub/TAK-NZ/CloudTAK`, `ANDROID-CloudTAK-${email}`). It appears in `ClientEndpoint.uid` and never in a certificate's `clientUid`, which is why a CloudTAK Device's two identifiers cannot match directly. Compared case-insensitively. See Requirement 22.
- **Connection_Alias**: The pure, total mapping from one reported `ClientEndpoint.uid` to the SET of `client_uid` values that uid may legitimately identify — its Candidate_Client_Uids. It exists because CloudTAK mints a Device's certificate identifier and its connection identifier in two unrelated places, so `ClientEndpoint.uid == tak_devices.client_uid` can never match a CloudTAK Device. See Requirement 22.
- **Candidate_Client_Uids**: The set a Connection_Alias derivation returns for a reported uid. It ALWAYS contains the reported uid itself, so a native ATAK/iTAK/WinTAK Device matches exactly as it does today; and WHERE the reported uid carries the CloudTAK_Connection_Prefix it additionally contains `<base> (Web)` and `<base> (ETL)`, where `<base>` is the remainder of the uid after that prefix. Every member is an exact string; the set is never a prefix, substring, or wildcard pattern. See Criteria 22.1, 22.2, 22.7.
- **Certificate_Uid_Suffix**: One of the two suffixes a CloudTAK-issued certificate's `clientUid` carries, distinguishing it from the bare account identifier: ` (ETL)`, applied by upstream `@tak-ps/node-tak` v12.24.0 (`dfpc-coe/node-tak`, `lib/api/credentials.ts:82`, `CredentialCommands.generate()`), and ` (Web)`, applied by the TAK-NZ fork only (`api/stateless/lib/authentik-provider.ts:623`, a file that does not exist upstream). A reported connection uid carries no evidence of which of the two minted a given certificate, which is why the Connection_Alias generates both. See Criterion 22.3.
- **DN_Shaped_Connection_Uid**: The third connection-uid form CloudTAK can produce — `ConnectionControl.uid(cert)`, the certificate subject reversed and comma-joined into a DN-shaped string — returned by `MachineConnConfig` and `AdminConnConfig` rather than by a user session. It is explicitly KNOWN-UNHANDLED by the Connection_Alias: no uid of this shape appeared in the 48 live Client_Endpoints_API entries, so nothing is built to match it. See Criterion 22.9.

## Requirements

### Requirement 1: Feature Flag and Inertness

**User Story:** As an operator, I want to enable or disable device management with a single server-side flag, so that deployments that do not use it incur none of its behavior.

#### Acceptance Criteria

1. THE Device_Management SHALL derive Device_Mgmt_Enabled as true WHEN `process.env.DEVICE_MGMT_ENABLED` equals the string `'true'`, and as false otherwise.
2. WHERE the `DEVICE_MGMT_ENABLED` environment variable is unset, THE Device_Management SHALL treat Device_Mgmt_Enabled as false.
3. THE Device_Management SHALL expose Device_Mgmt_Enabled through an `isDeviceMgmtEnabled()` function in `server/config/deviceMgmt.js`, analogous to `isCloudTakEnabled()` in `server/config/cloudtak.js`.
4. THE Device_Management SHALL read Device_Mgmt_Enabled on the server only and SHALL NOT include Device_Mgmt_Enabled in the response of the Public_Config_Endpoint in any case, including when the `DEVICE_MGMT_ENABLED` environment variable is unset.
5. WHILE Device_Mgmt_Enabled is false, THE Admin_Credential_Loader SHALL NOT load or refresh the Admin_Credential.
6. WHILE Device_Mgmt_Enabled is false, THE Subscription_Poller SHALL NOT call the Subscriptions_API.
7. WHILE Device_Mgmt_Enabled is false, THE Device_Sync SHALL NOT fetch Active_Certificates and SHALL NOT write to the Device_Table.
8. WHILE Device_Mgmt_Enabled is false, THE Device_Management SHALL make every device-management route and user-interface surface unreachable.
9. WHILE Device_Mgmt_Enabled is false, THE Device_Management SHALL NOT enqueue any Revoke_Operation on behalf of device management.

### Requirement 2: Admin Credential Loading and 24-Hour Refresh

**User Story:** As an operator, I want the TAK Server admin credential loaded from a configurable source (a Secrets Manager PKCS#12 bundle or the existing file/environment path) and refreshed on a schedule, so that a rotated credential is used without restarting the service and revocation and device-management share one credential mechanism.

#### Acceptance Criteria

1. WHEN `TAK_ADMIN_CERT_SOURCE` is `secrets-manager`, THE Device_Management SHALL select Credential_Source as `secrets-manager` and load the Admin_Credential from Secrets Manager; WHEN `TAK_ADMIN_CERT_SOURCE` is `file` or unset, THE Device_Management SHALL select Credential_Source as `file` (the default) and use the file/environment path.
2. WHILE Device_Mgmt_Enabled is true AND Credential_Source is `secrets-manager`, WHEN the service starts, THE Admin_Credential_Loader SHALL load the PKCS#12 Admin_Credential from Admin_Cert_Secret_Arn using a Binary_Secret_Read (reading `SecretBinary` as a Buffer), via the Secrets_Provider selected by `getSecretsProvider`.
3. THE Secrets_Provider SHALL provide a Binary_Secret_Read that returns a secret's raw `SecretBinary` as a Buffer, leaving the existing string `getSecret` behavior unchanged.
4. THE Admin_Credential_Loader SHALL open the loaded PKCS#12 bundle using P12_Passphrase, defaulting to `atakatak` when `TAK_ADMIN_CERT_PASSPHRASE` is unset and using `TAK_ADMIN_CERT_PASSPHRASE` when set.
5. THE Admin_Credential_Loader SHALL open the PKCS#12 bundle with P12_Passphrase and convert it to PEM certificate and private-key material, then cache the Admin_Credential in memory and expose it as `https.Agent` mutual-TLS options of the form `{ cert, key }` (with `{ ca }` when a CA bundle is configured). This conversion is required because the reference bundle uses legacy PKCS#12 algorithms that Node's TLS/OpenSSL 3 will not load directly as `pfx`; converting to PEM at load time (as CloudTAK does for the same secret) avoids depending on the OpenSSL legacy provider being enabled in the runtime.
6. WHILE Device_Mgmt_Enabled is true, THE Admin_Credential_Loader SHALL refresh the cached Admin_Credential every 24 hours as a scheduled job inside the Sync_Worker process alongside the existing `ExpiryScheduler` and `RetentionCleanupJob`.
7. WHEN a refresh yields a changed Admin_Credential, THE Device_Management SHALL rebuild the mutual-TLS agent and use the refreshed Admin_Credential for subsequent Marti `certadmin` API calls without a process restart (the current `TakServerService` builds its agent once in its constructor, so it SHALL be made refreshable).
8. THE single existing consumer of the Admin_Credential — the Sync_Worker's `revoke_tak_certificates` handler via `TakServerService` — SHALL use the same shared Admin_Credential_Loader, so revocation and device-management share one credential mechanism and both pick up a rotated credential without a restart.
9. WHERE Credential_Source is `file` (or unset), THE Device_Management SHALL build the mutual-TLS agent from the existing file/environment values (`TAK_API_P12_PATH`/`TAK_API_P12_PASSPHRASE` or `TAK_API_CERT_PATH`/`TAK_API_KEY_PATH`, plus optional `TAK_CA_PATH`), preserving the current `buildMutualTlsAgentOptions` behavior; and WHERE Credential_Source is `secrets-manager`, THE Device_Management SHALL NOT use file/environment credentials.
10. IF a scheduled Admin_Credential refresh fails, THEN THE Admin_Credential_Loader SHALL retain the previously cached Admin_Credential, log the failure via the Structured_Logger, and retry on the next scheduled refresh, without crashing or exiting the Sync_Worker process.
11. THE Admin_Credential_Loader SHALL NOT log the Admin_Credential material or the P12_Passphrase at any log level.
12. THE Admin_Credential_Loader SHALL correctly load a PKCS#12 bundle that uses legacy encryption algorithms (e.g. RC2/3DES), converting it to PEM at load time so that legacy-algorithm bundles are supported without requiring the OpenSSL legacy provider to be enabled in the Node runtime.

### Requirement 3: Last-Seen Polling and the Monotonic Guard

**User Story:** As a user, I want to see when each of my devices was last seen by TAK Server, so that I have a sense of recent device activity.

#### Acceptance Criteria

1. WHILE Device_Mgmt_Enabled is true, THE Subscription_Poller SHALL read the Client_Endpoints_API (`GET /Marti/api/clientEndPoints`) on a scheduled cadence, running inside the Sync_Worker process on its own timer. It SHALL NOT call `/Marti/clients`, which does not exist on TAK Server (404, and absent from `tak-server-openapispec.json`).
2. WHEN a poll returns a Client_Endpoints_API entry whose `uid` equals a Device's Client_Uid, THE Subscription_Poller SHALL record that Device's Last_Seen as that entry's `lastEventTime`, subject to the Monotonic_Guard. The Subscription_Poller SHALL NOT substitute the time of the observation for `lastEventTime`, and SHALL NOT require `lastStatus` to be `Connected` — a `Disconnected` entry carries the last-seen timestamp this feature exists to show (verified live: 46 of 48 entries were `Disconnected` and carried timestamps). **Amended in place (Requirement 20):** this criterion constrains the Last_Seen write ONLY. It says `lastStatus` SHALL NOT FILTER that write; it does not say `lastStatus` is unread. Requirement 20 reads the same field as the Connection_Status source, which narrows nothing here — every entry still contributes its `lastEventTime` whatever its `lastStatus`.
3. WHEN a scheduled poll would set a Device's Last_Seen to a value earlier than the Device's existing Last_Seen, THE Subscription_Poller SHALL leave the existing Last_Seen unchanged (the Monotonic_Guard applies during scheduled polls, protecting a stored value against a shrunk or rewound upstream history).
4. WHEN a poll returns no Client_Endpoints_API entry for a Device, THE Subscription_Poller SHALL leave that Device's existing Last_Seen unchanged and SHALL NOT null or rewind it.
5. WHERE TAK Server has never reported a Client_Endpoints_API entry for a Device across any poll, THE Device_Management SHALL represent that Device's Last_Seen as null and present it as "never seen".
6. THE Device_Management SHALL derive Last_Seen ONLY from TAK Server's Marti HTTP API and SHALL NOT query the TAK Server `cot_router` table or any TAK Server database directly.
7. THE Device_Management SHALL present Last_Seen as the last-seen time TAK Server itself reports for the Device, and SHALL NOT present it as a guaranteed-complete connection history — TAK Server may retain no entry for a Device, in which case Last_Seen is null.
8. IF a poll fails to reach the Client_Endpoints_API — including a 404, since that endpoint is documented in `tak-server-openapispec.json` and its absence means the request was wrong, not that no client has ever been seen — THEN THE Subscription_Poller SHALL log the failure as an error via the Structured_Logger, report the run as failed, leave all existing Last_Seen values unchanged, and retry on the next scheduled poll, without crashing or exiting the Sync_Worker process. THE Subscription_Poller SHALL NOT treat any failure as an empty result set (see Requirement 14).

### Requirement 4: Active-Certificate Sync and Local Persistence

**User Story:** As a user, I want my current devices tracked locally, so that the application can show my device list quickly and consistently.

#### Acceptance Criteria

1. THE Device_Management SHALL define a Device_Table via a `node-pg-migrate` incremental migration in `database/migrations`, following the existing migration conventions and baseline schema.
2. THE Device_Table SHALL have columns for `client_uid` (primary key), the associated local user, TAK certificate id, certificate issued timestamp, certificate expires timestamp, `last_seen_at` (nullable), `last_polled_at`, and a `revoked` boolean flag.
3. WHILE Device_Mgmt_Enabled is true, THE Device_Sync SHALL fetch BOTH the Active_Certificate view (`GET /Marti/api/certadmin/cert/active`) AND the Revoked_Certificate_View (`GET /Marti/api/certadmin/cert/revoked`) using `TakServerService`, and SHALL compute the Live_Certificates as the set difference (in `/active`, not in `/revoked`). Fetching `/active` alone is insufficient: verified live, 90 of the 95 certificates it returned were also in `/revoked`.
4. WHEN the Device_Sync processes the Live_Certificates, THE Device_Sync SHALL upsert exactly ONE Device_Table row per distinct `client_uid`, carrying the certificate id, issuance date, and expiration date of that Device's Newest_Live_Certificate — not one row per certificate, because many Live_Certificates commonly share one `client_uid`.
5. THE Device_Sync SHALL associate each Device_Table row with the local user whose TAK username matches the `creatorDn` of that Device's Newest_Live_Certificate, reusing the existing `TakServerService.findCertificatesForUser` / `matchesCreatorDn` matching logic.
6. THE Device_Management SHALL exclude superseded certificates from a Device's displayed attributes by selecting the Newest_Live_Certificate (greatest `issuanceDate`) locally. It SHALL NOT rely on the Active_Certificate view excluding them, and SHALL NOT use `GET /Marti/api/certadmin/cert/replaced` to exclude them: verified live, `/replaced` returned a set byte-identical to `/active` (the same 95 ids), so neither view distinguishes superseded certificates.
7. WHEN the Device_Sync completes a fetch, THE Device_Sync SHALL set `last_polled_at` on each upserted Device_Table row to the time of that sync run.
8. THE Device_Sync SHALL run using the existing Sync_Worker scheduled-job pattern and SHALL NOT introduce a new background-job framework.
9. IF the Device_Sync fails to fetch either the Active_Certificate view or the Revoked_Certificate_View — including a 404 from either, since both are documented in `tak-server-openapispec.json` — THEN THE Device_Sync SHALL log the failure as an error via the Structured_Logger, report the run as failed, leave existing Device_Table rows unchanged, and retry on the next scheduled run, without crashing or exiting the Sync_Worker process. THE Device_Sync SHALL NOT treat a failed Revoked_Certificate_View fetch as an empty revoked set, because that would present revoked certificates as live (see Requirement 14).

### Requirement 5: User Self-View of Devices

**User Story:** As a signed-in user, I want to see my own devices on the dashboard, so that I know which certificates are enrolled under my name and when each was last seen.

#### Acceptance Criteria

1. WHILE Device_Mgmt_Enabled is true, WHEN a signed-in user views the dashboard, THE Device_Management SHALL display that user's own Devices.
2. THE Device_Management SHALL display, for each Device, the device UID (`clientUid`), the issuance date, the expiration date, and the Last_Seen value.
3. WHERE a Device's Last_Seen is null AND that Device is not currently connected, THE Device_Management SHALL still display all of that Device's other details (device UID, issuance date, expiration date) and SHALL display "never seen" only in place of the Last_Seen value. **Amended in place (Requirement 20):** the not-currently-connected qualifier was added because a Device that TAK Server reports as connected is presented with the Connected_Label in that same cell whether or not a Last_Seen timestamp is known (Criterion 20.9); "never seen" would be a false statement about a Device that is connected right now.
4. THE Device_Management SHALL derive a user's device list from that user's Live_Certificates, one Device per `client_uid`, displaying each Device's Newest_Live_Certificate attributes — so that revoked and superseded certificates are not shown as Devices. A certificate present in the Active_Certificate view but also in the Revoked_Certificate_View SHALL NOT appear as a Device, and SHALL NOT be displayed with `revoked = false`.
5. THE Device_Management SHALL restrict the self-view so a user sees only that user's own Devices, enforced on the server and not solely in the user interface.

### Requirement 6: Admin View of Managed Users' Devices

4. THE Device_Management SHALL surface a Managed_User's device data in the Users view via a user-details modal that includes the device list.
5. THE Device_Management SHALL display, for each of a Managed_User's Devices, the device UID (`clientUid`), the issuance date, the expiration date, and the Last_Seen value, presenting a null Last_Seen as "never seen" WHERE that Device is not currently connected. **Amended in place (Requirement 20):** same qualifier and same reason as Criterion 5.3 — a currently-connected Device shows the Connected_Label in the Last Seen cell instead (Criterion 20.9), and both surfaces render that from the one shared row component.

### Requirement 7: Self-Service Device Revocation

**User Story:** As a signed-in user, I want to revoke one of my own devices with an explicit confirmation, so that I can disable a lost or retired device myself.

#### Acceptance Criteria

1. WHILE Device_Mgmt_Enabled is true, THE Device_Management SHALL allow a signed-in user to revoke one of that user's own Devices.
2. WHEN a user initiates revocation of a Device, THE Device_Management SHALL display a warning and require the user to type the Revoke_Confirmation_Word (`REVOKE`) exactly to confirm.
3. IF the confirmation text does not exactly equal the Revoke_Confirmation_Word, THEN THE Device_Management SHALL NOT proceed with the revocation and SHALL NOT enqueue the Revoke_Operation; THE Device_Management SHALL enqueue the Revoke_Operation only after the confirmation text has been validated as exactly equal to the Revoke_Confirmation_Word.
4. WHEN a user confirms revocation of that user's own Device, THE Device_Management SHALL enqueue the existing Revoke_Operation (`revoke_tak_certificates`) scoped to that Device's `client_uid`, covering ALL of that Device's Live_Certificates and NO certificate belonging to any other Device — including other Devices of the same user. Enqueuing the user-scoped `{ tak_usernames: [username] }` payload is NOT sufficient and is NOT permitted: the handler matches every certificate whose `creatorDn` matches the username, so it would revoke every certificate that user holds across all their Devices (see Requirement 12).
5. THE Device_Management SHALL restrict self-service revocation so a user can revoke only that user's own Devices, enforced on the server and not solely in the user interface.
6. WHEN the Revoke_Operation confirms revocation of a Device's Live_Certificates — confirmation meaning every targeted certificate id is present in the Revoked_Certificate_View on re-query, NOT that its `revocationDate` is non-null — THE Device_Management SHALL set that Device's Device_Table `revoked` flag to true.

### Requirement 8: Admin Revocation of a Managed User's Device

**User Story:** As an admin, I want to revoke a device of a user I directly manage with an explicit confirmation, so that I can disable a compromised or retired device on that user's behalf.

#### Acceptance Criteria

1. WHILE Device_Mgmt_Enabled is true, THE Device_Management SHALL allow an admin to revoke a Device of a Managed_User.
2. WHEN an admin initiates revocation of a Managed_User's Device, THE Device_Management SHALL display a warning and require the admin to type the Revoke_Confirmation_Word (`REVOKE`) exactly to confirm.
3. IF the confirmation text does not exactly equal the Revoke_Confirmation_Word, THEN THE Device_Management SHALL NOT proceed with the revocation.
4. WHEN an admin confirms revocation of a Managed_User's Device, THE Device_Management SHALL enqueue the existing Revoke_Operation (`revoke_tak_certificates`) scoped to that Device's `client_uid`, covering ALL of that Device's Live_Certificates and NO certificate belonging to any other Device of that user or of any other user (see Requirement 12).
5. THE Device_Management SHALL enforce strict authorization for admin revocation on the server, and not solely in the user interface, requiring both that the target user is a Managed_User of the acting admin AND that the target Device belongs to that user, blocking an unauthorized revocation attempt upfront before any Revoke_Operation is enqueued.
6. IF an admin attempts to revoke a Device of a user who is not a Managed_User of that admin, THEN THE Device_Management SHALL deny the request.
7. WHEN the Revoke_Operation confirms revocation of a Device's Live_Certificates — confirmation meaning every targeted certificate id is present in the Revoked_Certificate_View on re-query, NOT that its `revocationDate` is non-null — THE Device_Management SHALL set that Device's Device_Table `revoked` flag to true.

### Requirement 9: Logging, Security, and Authorization (Non-Functional)

#### Acceptance Criteria

1. THE Device_Management SHALL emit all server-side log output through the Structured_Logger and SHALL NOT use `console` logging in production code.
2. THE Device_Management SHALL log non-sensitive device-management operations via the Structured_Logger while excluding sensitive data, and SHALL NOT log the Admin_Credential material or any certificate passphrase at any log level.
3. THE Device_Management SHALL enforce self-view and self-revocation authorization so a user can view and revoke only that user's own Devices, on the server.
4. THE Device_Management SHALL enforce admin view and admin revocation authorization so an admin can view and revoke only Managed_Users' Devices, on the server.
5. WHILE Device_Mgmt_Enabled is false, THE Device_Management SHALL simultaneously disable all device-management operations — poll, sync, credential load, and enqueue — and SHALL make every device-management route unreachable, with no operation remaining active while others are disabled.
6. THE Device_Management SHALL provide server-side test coverage using the repository's jest test runner.
7. THE Device_Management SHALL provide client test coverage using the repository's vitest test runner.
8. THE Device_Management SHALL include a fast-check property test asserting that Last_Seen is monotonic-forward across successive poll observations (a poll observation never moves a Device's Last_Seen backward and never nulls an existing Last_Seen).
### Requirement 10: TAK Server TLS Server Identity Verification

**User Story:** As an operator, I want TAK Server's own TLS certificate verified against the name that certificate actually carries, so that the connection to the Marti API stays fully verified even though TAK Server is always reached under a different DNS name.

#### Acceptance Criteria

1. TAK Server presents a TLS server certificate whose subject and subjectAltName carry only its internal Expected_Server_Name (`CN=takserver`, a single `DNS:takserver` SAN) and not the DNS name operators dial (typically a load-balancer name such as `tak.example.tak.nz:8443`), so verifying that certificate's identity against the host of `TAK_SERVER_URL` always fails with `ERR_TLS_CERT_ALTNAME_INVALID`. THE Device_Management SHALL treat this as the expected shape of a TAK Server deployment — in production as well as in test environments — and SHALL NOT treat it as a misconfiguration to be worked around by weakening verification.
2. THE Mutual_TLS_Agent SHALL verify TAK Server's certificate chain against the Server_Trust_Bundle, so that a certificate the configured TAK CA did not issue is rejected.
3. THE Mutual_TLS_Agent SHALL NOT set `rejectUnauthorized: false` in any environment, including development and test. That single option disables chain verification as well as identity verification, so the agent would present the Admin_Credential — a TAK Server administrative client certificate — to whatever endpoint answered the connection, exposing it to any party able to intercept the connection.
4. WHERE `TAK_SERVER_TLS_SERVERNAME` is set to a non-empty value, THE Mutual_TLS_Agent SHALL set the TLS `servername` option to that value, so TAK Server's identity is verified against the Expected_Server_Name instead of the URL host, WHILE chain verification against the Server_Trust_Bundle continues to apply.
5. WHERE `TAK_SERVER_TLS_SERVERNAME` is unset or empty, THE Mutual_TLS_Agent SHALL NOT set a `servername` option and its behavior SHALL be unchanged — identity verified against the host of `TAK_SERVER_URL` — preserving current behavior for any deployment whose TAK Server certificate does match the dialed name.
6. THE Mutual_TLS_Agent SHALL apply Expected_Server_Name at agent-construction time, so every request made through the agent verifies against it, including the pre-existing Revoke_Operation path that shares `buildMutualTlsAgentOptions` with the device-management fetches (Requirement 2.8).
7. WHERE Credential_Source is `secrets-manager`, THE Server_Trust_Bundle MAY be derived from the CA certificates carried inside the Admin_Credential PKCS#12 bundle, which is obtained out-of-band relative to the connection being verified; THE Device_Management SHALL NOT derive the Server_Trust_Bundle from the TAK Server connection it is used to verify.
8. THE Device_Management SHALL NOT log the Admin_Credential material or the P12_Passphrase at any log level while satisfying this requirement; the non-logging constraints in 2.11 and 9.2 continue to apply unchanged and nothing new is logged (Expected_Server_Name is non-sensitive configuration, not a secret).

### Requirement 11: Device Identity Is a Client UID with a Set of Certificates

**User Story:** As a user, I want each of my devices to appear once, representing the device rather than one of the many certificates it has been issued, so that the list matches the devices I actually own.

#### Acceptance Criteria

1. THE Device_Management SHALL treat a Device as one Client_Uid together with the SET of Live_Certificates carrying that Client_Uid, and SHALL NOT treat one certificate as one Device. `clientUid` reuse is the normal case, not an anomaly: verified live, 95 certificates carried only 10 distinct `clientUid`s, with 60 certificates on `ckadmin (ETL)`, 12 on `etl-fenz-test (ETL)`, and 6 on `ANDROID-63040a40563b5fab`.
2. THE Device_Management SHALL compute a Device's Live_Certificates as those certificates that are present in the Active_Certificate view AND absent from the Revoked_Certificate_View, and SHALL treat this computed set — not the Active_Certificate view — as the live set.
3. THE Device_Management SHALL derive each Device's displayed certificate id, issuance date, and expiration date from that Device's Newest_Live_Certificate (greatest `issuanceDate`), computed locally.
4. THE Device_Management SHALL NOT use `GET /Marti/api/certadmin/cert/replaced` to identify superseded certificates, because that view returns the same set as the Active_Certificate view (verified live: the same 95 ids).
5. WHERE every certificate carrying a given Client_Uid is in the Revoked_Certificate_View, THE Device_Management SHALL NOT present that Client_Uid as a live Device, and in particular SHALL NOT present it with `revoked = false`. Applying Live_Certificate + Newest_Live_Certificate to the live server yielded exactly 1 live Device UID, where the earlier implementation listed 10, most of them revoked certificates shown as not revoked.
6. THE Device_Management SHALL keep exactly one Device_Table row per Client_Uid, so a re-enrollment that issues a new certificate for an existing Client_Uid updates that Device's row rather than creating a second Device.
7. THE Device_Management SHALL present CloudTAK-originated Devices — those whose Client_Uid identifies CloudTAK per Requirement 15 — as Devices alongside every other Device, and SHALL allow them to be revoked. They are not filtered out.

### Requirement 12: Device-Scoped Revocation and Revocation Verification

**User Story:** As a user, I want revoking one device to affect only that device, and to be reported as successful only when TAK Server actually lists its certificates as revoked, so that revocation is neither too broad nor falsely confirmed.

#### Acceptance Criteria

1. WHEN Device_Management revokes a Device, THE Revoke_Operation SHALL target exactly the certificate ids of that Device's Live_Certificates, and SHALL NOT target any certificate carrying a different Client_Uid — including certificates issued to the same local user for a different Device.
2. THE Revoke_Operation payload SHALL become device-scoped, carrying the target `client_uid` (and the certificate ids or the target user id needed for traceability) rather than only `tak_usernames`. This changes the `revoke_tak_certificates` schema in `server/workers/operationSchemas.js`, whose `requiredFields` are currently `{ tak_usernames: 'object' }`, and the `revokeTakCertificates` handler in `server/workers/syncWorker.js`, which currently matches every certificate whose `creatorDn` matches a payload username.
3. THE Device_Management SHALL preserve the existing user-scoped behavior for the pre-existing call sites that legitimately revoke everything a user holds (`TakCertificateRevocationService.revokeUserTakCertificates`, `TeamMembershipService.removeUserFromTeam`'s no-teams-left branch, and `Team.delete`'s bulk enqueue), so the device-scoped payload is an ADDITION to the operation's contract rather than a replacement that breaks main-spec Requirement 26.6/26.7.
4. THE Device_Management SHALL verify a revocation by re-querying the Revoked_Certificate_View (`GET /Marti/api/certadmin/cert/revoked`) and confirming every targeted certificate id is present in it.
5. THE Device_Management SHALL NOT verify a revocation by checking that a certificate's `revocationDate` is non-null. That check cannot distinguish revoked from live certificates: verified live, all 95 certificates in the Active_Certificate view carried a non-null `revocationDate`, including the 5 that TAK Server does NOT list under `/revoked` (for example id 3212, `revocationDate: 2026-01-17T01:15:22.160Z`, absent from `/revoked`). A `revocationDate`-based check therefore reports success unconditionally.
6. THE Device_Management SHALL apply the corrected verification in `TakServerService.revokeCertificates`, which today re-queries `listCertificates()` and treats a non-null `revocationDate` as confirmation. Because that method is shared, this corrects the verification of the pre-existing main-spec Requirement 26 revoke path as well as this feature's, and that scope SHALL be called out in review.
7. IF any targeted certificate id is absent from the Revoked_Certificate_View on re-query, THEN THE Device_Management SHALL report the revocation as unverified and SHALL NOT set the Device_Table `revoked` flag, preserving the existing retryable-failure semantics.
8. THE Device_Management SHALL set the Device_Table `revoked` flag only for the `client_uid` whose Live_Certificates were confirmed revoked, and SHALL NOT flip the flag for any other Device of the same user.
9. THE Device_Management SHALL gate reading Devices — the self-view, the admin view, the Subscription_Poller and the Device_Sync — on Device_Mgmt_Enabled alone, and SHALL additionally require Revoke_Enabled before any revoke is issued; Revoke_Enabled SHALL default to false and SHALL be derived from `DEVICE_MGMT_REVOKE_ENABLED` independently of `DEVICE_MGMT_ENABLED`. The reason the destructive capability needs its own flag: with a single flag, enabling the feature in order to look at a device list also arms certificate revocation, so an operator who wants only visibility cannot get it without also making the revoke path live.
10. WHILE Revoke_Enabled is false, THE Device_Management SHALL NOT enqueue a Revoke_Operation from either revoke route, and SHALL respond with a distinct, non-404 client error whose body names the disabled capability. It SHALL NOT respond 404, because 404 is the response that already means Device_Mgmt_Enabled is off (Requirement 1.8), and a caller could not tell "device management is absent" from "revocation is disarmed".
11. WHILE Revoke_Enabled is false, IF a Revoke_Operation nevertheless exists in the `sync_operations` queue — enqueued by a pre-existing user-scoped call site, by an earlier deployment, or by hand — THEN the handler SHALL log the complete Revoke_Audit_Record, SHALL NOT issue the `DELETE /Marti/api/certadmin/cert/revoke/{ids}`, SHALL NOT set the Device_Table `revoked` flag, and SHALL complete the operation as a Revoke_Dry_Run rather than reporting it as failed.
12. WHEN a device-scoped Revoke_Operation resolves its target certificates, THE Device_Management SHALL require that the resolved set carries exactly ONE distinct `client_uid`; IF the resolved set spans more than one `client_uid`, THEN the operation SHALL abort without issuing the `DELETE` and SHALL be marked permanently failed rather than retried, because a resolution that spans Devices is a defect that retrying cannot fix.
13. THE Device_Management SHALL check the resolved target count against the Revoke_Blast_Radius_Cap (`DEVICE_MGMT_REVOKE_MAX_CERTS`, documented default 250) BEFORE issuing the `DELETE`, and IF the count exceeds the cap THEN the operation SHALL abort without issuing the `DELETE`. THE Device_Management SHALL NOT truncate the target set to the cap and proceed: a partial revocation reports a Device as disabled while leaving it usable, which is worse than a refused revocation. The default SHALL exceed the largest real per-Device certificate count observed on the live server (60 certificates on `ckadmin (ETL)`), so that a legitimate re-enrollment-heavy Device is not blocked by the cap.
14. THE Device_Management SHALL log the Revoke_Audit_Record — the target `client_uid`, every targeted certificate id, the resolved count, the acting user, and the operation id — via the Structured_Logger BEFORE issuing the `DELETE`, and SHALL log the verification outcome (per Criteria 12.4–12.7) after it. The certificate id list SHALL NOT be truncated in the log; WHERE the resolved count makes a full list impractical, THE Device_Management SHALL log the count and a stable digest of the sorted id list alongside whatever ids it does record. The reason this is a requirement rather than a nicety: when 20 certificates were revoked on the shared live TAK Server during this feature's enablement, the only reason "did we revoke these?" was answerable at all was the `sync_operations` queue table, and any revoke issued outside that queue would have left no trace to answer it with.
15. THE Device_Management SHALL apply the Revoke_Blast_Radius_Cap check (12.13) and the Revoke_Audit_Record (12.14) to BOTH payload shapes of the Revoke_Operation — the device-scoped `client_uid` shape AND the pre-existing user-scoped `tak_usernames` shape — since the user-scoped shape is the one with the larger blast radius. The single-`client_uid` constraint in 12.12 applies to the device-scoped shape only, because the user-scoped shape legitimately spans a user's Devices (Requirement 12.3).
16. THE Device_Management SHALL record, as part of the Revoke_Audit_Record and its post-action counterpart, the pre-flight and post-flight certificate counts of the Revoked_Certificate_View, so that what a revoke changed on TAK Server is answerable by differencing two recorded counts rather than by inferring it from an absence of evidence.

### Requirement 13: Last_Seen from TAK Server's Client Endpoints History

**User Story:** As a user, I want last-seen to come from TAK Server's own record of when it last heard from each client, so that a device that has been offline since before this feature was installed still shows a real last-seen time.

#### Acceptance Criteria

1. THE Device_Management SHALL source Last_Seen from the Client_Endpoints_API's `ClientEndpoint.lastEventTime`, matching a Client_Endpoints_API entry to a Device by `ClientEndpoint.uid == tak_devices.client_uid`.
2. THE Device_Management SHALL NOT source Last_Seen from `GET /Marti/api/subscriptions/all` (`SubscriptionInfo`). Although that schema carries a `clientUid`, the field was empty in 14 of 16 live entries, so it is not a usable key source.
3. THE Device_Management SHALL NOT depend on repeated polling to reconstruct last-seen history, because the Client_Endpoints_API already returns TAK Server's recorded history including disconnected clients. The best-effort monotonic reconstruction the earlier design was built around is therefore largely unnecessary.
4. THE Device_Management SHALL retain the Monotonic_Guard as a guard: a later poll SHALL NOT rewind or null a stored `last_seen_at`, even though the guard is no longer the mechanism by which history is accumulated.
5. THE Device_Management SHALL keep Requirement 9.8's fast-check property test required, applying it to the Monotonic_Guard: across all sequences of reported `lastEventTime` values for a Device, the stored Last_Seen equals the running maximum and is never nulled once set.
6. WHERE a Client_Endpoints_API entry's `lastEventTime` is absent or unparseable, THE Device_Management SHALL leave that Device's stored Last_Seen unchanged rather than writing a null or an invalid timestamp.
7. THE Device_Management MAY pass the Client_Endpoints_API's documented query parameters (`secAgo`, `showCurrentlyConnectedClients`, `showMostRecentOnly`, `group`), and WHERE it does so it SHALL NOT narrow the result to currently-connected clients only, since the disconnected entries are the ones carrying the last-seen timestamps of interest.

### Requirement 14: Documented Endpoints Must Fail Loudly

**User Story:** As an operator, I want a request to an endpoint that is supposed to exist to fail visibly when it does not, so that a wrong URL cannot look like an empty server.

#### Acceptance Criteria

1. WHERE an endpoint is documented as existing in `tak-server-openapispec.json`, IF a request to it fails — including with a 404 — THEN THE Device_Management SHALL log the failure as an error via the Structured_Logger and report the containing run or operation as failed, and SHALL NOT degrade the failure to an empty result set.

3. THE Device_Management SHALL treat as genuinely optional only those views it does not require to produce correct output, and SHALL record in code, at each tolerated-absence site, which OpenAPI operation the view corresponds to and why its absence is safe.
4. THE Device_Management SHALL NOT call an endpoint that is absent from `tak-server-openapispec.json`. `/Marti/clients` is absent from it and returns 404 on the live server, so `getConnectedSubscriptions()`'s target SHALL be replaced rather than tolerated.
5. THE Device_Management SHALL make the failure of a documented-endpoint fetch distinguishable in logs from a successful fetch that legitimately returned zero rows, so that "no devices" and "the request was wrong" are never reported identically. This is the specific defect Requirement 3.8's earlier graceful-404 handling produced: a non-existent endpoint silently became "no clients observed", Last_Seen stayed null indefinitely, and no error was ever surfaced.

### Requirement 15: Client Type Classification

7. THE Device_Management SHALL implement Device_Type_Icons as inline SVG glyphs committed in the repository within a single `DeviceTypeIcon` component and SHALL NOT add a new client dependency for them. It MAY use the already-present `@heroicons/react` `GlobeAltIcon` for CloudTAK and `QuestionMarkCircleIcon` for Unknown.
8. THE Device_Management SHALL cover every classification rule, the CloudTAK-over-Android precedence, and the Unknown fallback with tests, including a fast-check property asserting that classification is total (every string maps to exactly one Client_Type) and case-insensitive.

### Requirement 17: Stale Device Rows Are Deleted by the Sync

**User Story:** As a user, I want a device whose certificates have all been revoked to disappear from my device list, so that the list shows the devices I actually hold rather than every device I have ever held.

Requirement 11.5 establishes that a Client_Uid whose every certificate is revoked is never presented as a live Device. It is satisfied for the WRITE side only: such a Client_Uid yields no group, so it is never upserted and can never appear with a freshly-written `revoked = false`. Nothing removes a Device_Table row that was upserted while the Client_Uid was still live, and no read path filters one out — `DeviceManagementService.listOwnDevices` filters on `user_id` alone, with no freshness check and no `revoked` check. So the row keeps being returned by the self-view and the admin view indefinitely. Observed live: TAK Server held 13 Live_Certificates yielding 13 Devices while `tak_devices` held 22 rows; nine were stale, six of them one user's, every one of them with `revoked = false` and a `last_polled_at` hours older than the newest successful sync (for example `95623A24-71A4-4FCC-98ED-FCA7C2DEFA27`, `ANDROID-25852d3229de5f89`, `chris@chriselsen.net (ETL)`, `kingston.kokako@tak.nz (ETL)`, `S-1-5-21-1407069837-2091007605-538272213-25045379`, `twoodill@amazon.com (ETL)`).

The chosen close is deletion during the sync. It is available now specifically because of Criterion 13.1: since Last_Seen is sourced from TAK Server's own reported `lastEventTime` rather than accumulated by our polling, a deleted row's `last_seen_at` is re-derivable on the next poll whenever TAK Server still reports that Client_Uid, so deletion no longer destroys history the way it would have under the earlier accumulate-by-polling design.

#### Acceptance Criteria

1. WHEN a Device_Sync run has fetched the Live_Certificates successfully and derived its Live_Device_Set, THE Device_Sync SHALL delete every Stale_Device_Row — every Device_Table row whose `client_uid` is absent from that Live_Device_Set.
2. IF a Device_Sync run reports its outcome as failed — a failed certificate-view fetch, a payload that is not a certificate list, or a failed local-user load, each of which ends the run before any write and reports `outcome: 'failed'` (Criteria 4.9, 14.1, 14.5) — THEN THE Device_Sync SHALL delete no Device_Table row. This is the load-bearing safety constraint of this requirement: a TAK Server outage that produced an empty or unreadable response SHALL leave the Device_Table exactly as it was rather than emptying it.
3. THE Device_Sync SHALL restrict every deletion to the `client_uid` values absent from the Live_Device_Set, and SHALL NOT issue a deletion that is unrestricted by `client_uid`.
4. THE Device_Sync SHALL retain every Device_Table row whose `client_uid` is present in the Live_Device_Set, so a Client_Uid that does hold a Live_Certificate is never deleted — Criterion 11.5's failure mode from the opposite direction, hiding a live Device.
5. WHEN a Client_Uid that was previously deleted appears in the Live_Certificates of a later run, THE Device_Sync SHALL create one Device_Table row for that Client_Uid through the existing upsert (Criterion 4.4), taking `revoked` from its column default of false; and THE Subscription_Poller SHALL re-populate that row's `last_seen_at` from the Client_Endpoints_API's reported `lastEventTime` (Criteria 13.1, 3.2).
6. IF the deletion fails, THEN THE Device_Sync SHALL log the failure via the Structured_Logger, complete the remainder of that run, and retry the deletion on the next scheduled run — matching how a single row's failed upsert is already logged and skipped rather than aborting the pass (Criterion 4.9); THE Device_Sync `run()` SHALL continue never to throw.
7. WHERE every certificate carrying a Device_Table row's `client_uid` is in the Revoked_Certificate_View — which is the state a confirmed revocation leaves behind, and the state in which that row's `revoked` flag was set true (Criteria 7.6, 8.7) — THE Device_Sync SHALL delete that row on the next run whose outcome is completed. THE Device_Management SHALL therefore present the "Revoked" badge as the transient state between a confirmed revocation and the next completed sync, and SHALL NOT present it as a permanent record that a revocation occurred; the durable record of a revocation is the `sync_operations` row and the Revoke_Audit_Record (Criterion 12.14).
8. THE Device_Management SHALL determine whether a Device appears in the self-view and the admin view from the presence of its Device_Table row alone, and SHALL NOT add a `last_polled_at` freshness filter or a `revoked` filter to `DeviceManagementService.listOwnDevices`, so that the removal of stale Devices has exactly ONE mechanism rather than a deletion and a redundant read-side filter that can disagree.
9. WHEN a Device_Sync run completes, THE Device_Sync SHALL report the number of deleted Device_Table rows in that run's `outcome: 'completed'` log line alongside the existing per-run counts, so that a deletion is observable rather than inferred (consistent with Criterion 14.5).

### Requirement 18: Configurable Display Timezone, Applied App-Wide

**User Story:** As an operator, I want every date the application shows to be rendered in a timezone I configure, so that a user in New Zealand reading a TAK Server timestamp sees the local wall-clock time rather than whatever zone their browser happens to be in.

Verified live: TAK Server reported `2026-03-12T00:58:04.508Z` for a Device and the user interface rendered `2026-03-11 17:58` — UTC−7, the browser's zone, seven hours and a calendar day away from the operator's. The cause is in the Date_Format_Helpers: `formatDate`/`formatDateTime` build their output from `date.getFullYear()`, `getMonth()`, `getDate()`, `getHours()` and `getMinutes()`, every one of which is a browser-local-time getter.

**Scope note — this requirement deliberately reaches outside device-management, and that is the chosen scope, not an oversight.** The fix lands inside the shared Date_Format_Helpers, so it changes the rendered output of every date in the application: the device lists, the Users view, the audit log, the requests lists, the admin surfaces, and the org-interest requests. Dates on pages that have nothing to do with device management WILL shift. That is the point — a per-feature timezone would mean two dates on one screen in two zones — but it is the single widest-reaching change in this spec and **it needs flagging in review**, alongside the two out-of-scope reaches already recorded (the shared `revokeCertificates` verification fix and the shared `buildMutualTlsAgentOptions` `servername`).

#### Acceptance Criteria

1. THE Device_Management SHALL derive the Display_Timezone from the `DISPLAY_TIMEZONE` environment variable, and WHERE that variable is unset or empty THE Device_Management SHALL use `Pacific/Auckland`.
2. THE Date_Format_Helpers SHALL compute the year, month, day, hour and minute components of every value they render from the instant's wall-clock time in the Display_Timezone, rather than from the browser's local zone.
3. THE Date_Format_Helpers SHALL emit exactly the format they emit today — `yyyy-mm-dd` from `formatDate` and `yyyy-mm-dd HH:MM` on a 24-hour clock from `formatDateTime`, every component zero-padded — so that only the zone the components are computed in changes. A locale-dependent rendering (the `toLocaleDateString`/`toLocaleTimeString`-style output the Date_Format_Helpers exist to replace, per their own doc comment) SHALL NOT be emitted, because it would violate the locale-independent format convention this application standardises on.
4. THE Display_Timezone SHALL apply to every user-visible date the application renders through the Date_Format_Helpers, and SHALL NOT be scoped to device-management surfaces.
5. THE Public_Config_Endpoint SHALL include the resolved Display_Timezone as a `display_timezone` Presentation_Config key, so the value reaches the client that renders the dates.
6. THE Device_Management SHALL keep Device_Mgmt_Enabled and Revoke_Enabled out of the Public_Config_Endpoint response exactly as Criteria 1.4 and 12.9 require, and SHALL NOT treat Criterion 18.5 as a precedent for exposing either. The distinction is the reason 18.5 is safe and 1.4/12.9 are not negotiable: a display timezone is presentation, carries no security meaning, arms no capability, and is useless on the server; the two device-management flags describe the arming state of a destructive capability. A future reader finding a device-management-adjacent environment value in the public config SHALL read this criterion before concluding it is a mistake to be corrected.
7. WHERE the Public_Config_Endpoint is unreachable, or its response omits the `display_timezone` key, THE Date_Format_Helpers SHALL render in `Pacific/Auckland` — the same literal default Criterion 18.1 names — so that a client that never received the configuration behaves identically to one that received the default.
8. IF the resolved Display_Timezone is not a zone the client runtime recognises, THEN THE Date_Format_Helpers SHALL apply the Display_Timezone_Fallback_Chain and continue to return a correctly formatted date, and SHALL NOT raise, SHALL NOT return the empty string, and SHALL NOT return the caller's fallback value for an instant that is parseable. A mistyped `DISPLAY_TIMEZONE` SHALL cost the application its configured zone and nothing else.
9. THE Date_Format_Helpers SHALL resolve and validate the Display_Timezone once and reuse that resolution for subsequent calls, rather than re-validating on every rendered date.
10. THE Date_Format_Helpers SHALL preserve their existing behaviour for input that is null, undefined, or unparseable: the caller's `fallback` argument is returned, defaulting to the empty string.
11. THE Device_Management SHALL install the resolved Display_Timezone before the first user-visible date is rendered, and WHERE the Public_Config_Endpoint response has not arrived THE Device_Management SHALL render with the Criterion 18.7 default rather than blocking the interface on it.
12. THE Display_Timezone SHALL affect presentation only: THE Device_Management SHALL continue to store, log, and transport every timestamp as it does today (ISO-8601, UTC), and SHALL NOT convert a stored value, a Structured_Logger field, or an API response field into the Display_Timezone.
13. THE Device_Management SHALL document `DISPLAY_TIMEZONE` in `.env.example` as an optional variable with its `Pacific/Auckland` default and a note that it applies app-wide, and SHALL NOT add it to `REQUIRED_VARS`.
14. THE Device_Management SHALL cover the Display_Timezone rendering, the format invariance, and the never-raise obligation of Criterion 18.8 with a fast-check property test, in addition to unit tests for the specific zones and boundaries.

### Requirement 19: The Device List Auto-Refreshes Without a Page Reload

**User Story:** As a signed-in user, I want my device list to keep itself current while I have the dashboard open, so that I do not have to reload the page to see a device's state change.

The Dashboard's device fetch runs once on mount and again after a revoke; there is no polling. The channel-data card in the same file already auto-refreshes on a 60000 ms interval with a `visibilitychange` pause that refreshes immediately when the tab becomes visible again — the Visibility_Pause_Pattern.

#### Acceptance Criteria

1. WHILE the Dashboard "My Devices" card is mounted and the browser tab is visible, THE Device_Management SHALL re-fetch the device list every Device_List_Refresh_Interval (60000 ms) without a page reload.
2. THE Device_Management SHALL implement Criterion 19.1 by reusing the Visibility_Pause_Pattern already present in `client/src/pages/Dashboard.jsx` — clear the interval WHILE the tab is hidden, re-fetch immediately WHEN it becomes visible again, then restart the interval — and SHALL NOT introduce a second, differently-behaved refresh mechanism beside it.
3. WHEN the Dashboard unmounts, THE Device_Management SHALL clear the device-refresh interval and remove its `visibilitychange` listener, so no timer survives the component.
4. WHILE a revoke confirmation dialog is open, THE Device_Management SHALL leave that dialog open, leave the Device it targets selected, and leave any text the user has typed into it intact across a refresh.
5. IF a refresh fetch fails, THEN THE Device_Management SHALL continue to display the most recently fetched device list unchanged, and SHALL NOT clear the list, SHALL NOT return the card to its loading state, and SHALL NOT render the empty-list message. A refresh failure MAY be surfaced as an inline indicator alongside the retained list.
6. WHILE the card is displaying a successfully fetched list, THE Device_Management SHALL keep the card rendered until a later fetch either succeeds or reports the feature as disabled, so that a transient failure does not make the card disappear.
7. THE Device_Management SHALL leave the server-side cadences unchanged: the Subscription_Poller keeps its `DEVICE_MGMT_POLL_INTERVAL_MS` cadence (default 5 minutes) and the Device_Sync its `DEVICE_MGMT_SYNC_INTERVAL_MS` cadence (default 15 minutes). A client refresh therefore mostly re-reads rows the server has not changed; the 60000 ms figure is chosen for consistency with the channel-data card in the same view rather than because the underlying data changes that often, and Criterion 19.1 SHALL NOT be read as a requirement for fresher server-side data.
8. THE Device_Management SHALL NOT auto-refresh the user-details device modal: it fetches on open and after a revoke, and it is a short-lived dialog a user opened deliberately, where a background re-render is disruption rather than freshness.

### Requirement 20: A Currently-Connected Device Is Presented as Connected

**User Story:** As a user, I want a device that is connected to TAK Server right now to say so, so that I am not left inferring a live connection from a timestamp in the past.

`ClientEndpoint.lastStatus` is `Connected` or `Disconnected`, and the Subscription_Poller currently reads `uid` and `lastEventTime` from each entry and discards it. Verified live: 2 of 48 entries were `Connected` and 46 `Disconnected`.

#### Acceptance Criteria

1. WHERE TAK Server reports a Device as currently connected, THE Device_Management SHALL present that Device as connected rather than presenting only a past Last_Seen timestamp.
2. THE Device_Management SHALL persist Connection_Status on the Device_Table as a `connected` boolean column, added by a `node-pg-migrate` incremental migration following the existing conventions, with a default of false. Connection_Status is stored rather than derived because it is current state read from TAK Server: it is not a function of any certificate attribute the Device_Table already holds, so there is nothing to derive it from on read the way Client_Type is derived from Client_Uid (Criterion 15.2).
3. WHEN a poll succeeds, THE Subscription_Poller SHALL write Connection_Status for EVERY `uid` the Client_Endpoints_API reported, independently of whether that Device's Last_Seen moved forward. THE Subscription_Poller SHALL NOT place the Connection_Status write behind the Monotonic_Guard's `last_seen_at IS NULL OR last_seen_at < $2` predicate: Connection_Status is current state, not a running maximum, so a Device that is connected right now but whose reported `lastEventTime` has not advanced past the stored value would never have its status updated if the two writes shared that guard. This is the load-bearing constraint of this requirement.
4. WHEN a Client_Endpoints_API entry is skipped for carrying an absent or unparseable `lastEventTime` (Criterion 13.6), THE Subscription_Poller SHALL still record that entry's contribution to Connection_Status, so that an unusable timestamp costs a Device its Last_Seen update and not its status.
5. WHEN several Client_Endpoints_API entries report the same `uid`, THE Subscription_Poller SHALL apply the Status_Collapse_Rule: the Device is connected WHEN at least one of those entries reports `lastStatus` equal to `Connected` compared case-insensitively, and is not connected otherwise. The reason ANY rather than the newest or the majority: a device with one live connection is connected, and TAK Server holds stale per-callsign entries for the same UID alongside the live one — verified live, one Windows SID returned four entries under different callsigns. A `lastStatus` that is absent, null, or any other value SHALL count as not connected.
6. WHEN a poll succeeds and the Client_Endpoints_API reported no entry at all for a Device_Table row's `client_uid`, THE Subscription_Poller SHALL set that Device's Connection_Status to not connected, and SHALL restrict that write to the `client_uid` values absent from the reported set rather than issuing an update unrestricted by `client_uid` (the same scoping discipline Criterion 17.3 requires of the stale-row deletion). "Connected" is a claim that requires positive evidence from the current poll: leaving a stale true in place would present a Device as online indefinitely if TAK Server stopped reporting it, whereas the cost of this rule being wrong is that a connected Device reads as not connected for at most one poll interval. Criterion 3.4 is unaffected — that Device's Last_Seen is still left exactly as it was.
7. IF a poll fails, or returns a payload that is not a list, THEN THE Subscription_Poller SHALL write no Connection_Status at all, leaving every stored value exactly as it was, consistent with Criteria 3.8, 14.1 and 17.2. THE Subscription_Poller SHALL NOT mark every Device not connected because a poll failed: a TAK Server outage would then be indistinguishable from every device having gone offline.
8. THE Device_Management SHALL expose Connection_Status as a `connected` boolean on the Device wire shape through `mapDevice`, the single wire-shape definition every device endpoint already returns through, so all four endpoints gain the field at once and no surface can see it while another does not.
9. WHERE a Device is connected, THE Device_Management SHALL present the Connected_Label as text in that Device's Last Seen cell, and SHALL additionally present the Last_Seen timestamp beside it WHERE one is known, so that adopting the label costs no information. THE Device_Management SHALL NOT convey the connected state by colour alone — the state SHALL be carried by text a screen reader announces, following the convention Criterion 16.5 establishes for the revoked state — and SHALL render it from the one shared device-list row component, so the Dashboard card and the user-details modal cannot diverge (Criterion 16.6).
10. THE Device_Sync SHALL NOT write the `connected` column, exactly as it does not write `last_seen_at` or `revoked`: an inserted row takes the column default, and an upsert leaves any stored value untouched. Connection_Status has one writer, the Subscription_Poller.
11. WHEN a Device_Table row is deleted as a Stale_Device_Row (Criterion 17.1) and its `client_uid` later re-appears in the Live_Certificates, THE Device_Sync SHALL create that row with `connected` at its column default of false, and THE Subscription_Poller SHALL re-derive it on the next successful poll.
12. THE Device_Management SHALL cover the Status_Collapse_Rule and the independence of the Connection_Status write from the Monotonic_Guard with a fast-check property test, in addition to unit tests for the no-entry, failed-poll, and unparseable-`lastEventTime` cases.

### Requirement 21: An Imminent Certificate Expiry Is Highlighted

**User Story:** As a user, I want a device whose certificate is about to expire to stand out in the list, so that I re-enroll it before it stops working rather than after.

#### Acceptance Criteria

1. THE Device_Management SHALL derive Expiry_Warning_Days from the `DEVICE_MGMT_EXPIRY_WARNING_DAYS` environment variable, defaulting to 30, and WHERE that variable is unset, unparseable, zero, or negative THE Device_Management SHALL use 30 — the same `parseInt(...) || <default>` discipline `getRevokeMaxCerts()` already follows for `DEVICE_MGMT_REVOKE_MAX_CERTS`.
2. WHERE a Device's `expires_at` is an Imminent_Expiry, THE Device_Management SHALL render that Device's Expires value in bold and in red.
3. THE Device_Management SHALL accompany the bold-red rendering of Criterion 21.2 with a text marker that a screen reader announces, and SHALL NOT convey an Imminent_Expiry by colour alone — nor by colour and weight alone, since font weight is no more perceivable to a screen reader than colour is. This follows the convention Criterion 16.5 already establishes for the revoked state, whose "Revoked" text badge beside the UID is what carries that state to assistive technology.
4. WHERE a Device's `expires_at` is null, THE Device_Management SHALL apply no expiry highlighting and no text marker, and SHALL leave that cell's existing rendering unchanged.
5. WHERE a Device's `expires_at` is a known instant already in the past, THE Device_Management SHALL render it in the Expired_Certificate_State: the same bold-red treatment as an Imminent_Expiry, with a DIFFERENT text marker. The two states are deliberately distinguished rather than styled identically, because a marker reading "expires soon" is a false statement about a date that has passed, and the two call for different action — re-enroll before the deadline versus re-enroll now, the device is already refusing connections.
6. THE Device_Management SHALL classify every Device's `expires_at` into exactly one of three states — no highlighting, Imminent_Expiry, or Expired_Certificate_State — with these boundaries: an `expires_at` strictly earlier than now is Expired_Certificate_State; an `expires_at` from now up to and including now plus Expiry_Warning_Days is Imminent_Expiry; an `expires_at` later than that, or null or unparseable, is no highlighting. The boundary is inclusive, so an `expires_at` falling exactly on now plus Expiry_Warning_Days is an Imminent_Expiry.
7. THE Public_Config_Endpoint SHALL include the resolved Expiry_Warning_Days as a `device_expiry_warning_days` Presentation_Config key, reaching the client the same way the Display_Timezone does and subject to the same Criterion 18.6 reasoning; and WHERE that response is unreachable, omits the key, or carries a value that is not a positive integer, THE Device_Management SHALL apply 30 client-side.
8. THE Device_Management SHALL apply Criteria 21.2–21.6 identically in the Dashboard "My Devices" card and in the user-details modal, rendered from the one shared device-list row component (Criterion 16.6).
9. THE Device_Management SHALL treat the still-live, nearly-expired certificate as the case this requirement exists for. The Expired_Certificate_State of Criterion 21.5 is specified for completeness and is not assumed to be reachable: whether a fully-expired certificate remains in the Active_Certificate view has NOT been verified against the live server, so a Device may lose its Device_Table row to the Stale_Device_Row deletion (Criterion 17.1) at or before expiry and never render in that state at all. THE Device_Management SHALL NOT add an expiry filter to the read path to force either outcome — Criterion 17.8 stands, and visibility has exactly one mechanism.
10. THE Device_Management SHALL document `DEVICE_MGMT_EXPIRY_WARNING_DAYS` in `.env.example` as an optional variable with its default of 30, alongside the existing device-management variables, and SHALL NOT add it to `REQUIRED_VARS`.
11. THE Device_Management SHALL cover the three-way classification of Criterion 21.6 and its exact boundaries with a fast-check property test, in addition to unit tests for the null, past, on-boundary, and far-future cases.

### Requirement 22: A CloudTAK Device's Last_Seen Is Matched Through Its Connection Alias

**User Story:** As a CloudTAK user, I want my browser session's device row to show when it was last seen, so that a device I am actively using does not read as "never seen".

Verified live: `chris@chriselsen.net (Web)` renders as "never seen" while the device is in use. The cause is not a missing entry — TAK Server holds one — but a join that cannot match. Criterion 13.1 matches a Client_Endpoints_API entry to a Device by `ClientEndpoint.uid == tak_devices.client_uid`, and for a CloudTAK Device those two strings are minted in two unrelated places:

| `tak_devices.client_uid` (from the certificate) | direct match in `clientEndPoints`? | reported `uid` |
|---|---|---|
| `ANDROID-63040a40563b5fab` (native ATAK) | yes | same string |
| `chris@chriselsen.net (Web)` | no | `ANDROID-CloudTAK-chris@chriselsen.net` |
| `ckadmin (ETL)` | no | `ANDROID-CloudTAK-ckadmin` |

Provenance, established by reading the CloudTAK source at `/home/ubuntu/GitHub/TAK-NZ/CloudTAK`: the certificate `clientUid` gets its ` (ETL)` suffix from **upstream** `@tak-ps/node-tak` v12.24.0 (`dfpc-coe/node-tak`, `lib/api/credentials.ts:82`, `CredentialCommands.generate()`); it gets its ` (Web)` suffix from the **TAK-NZ fork only** (`api/stateless/lib/authentik-provider.ts:623`, a file absent upstream); and the connection/CoT uid is `ANDROID-CloudTAK-${email}` from **upstream** CloudTAK (`api/common/connection-config.ts:170`). Nothing in the reported uid records which of the two certificate paths was taken.

The chosen close is a Connection_Alias applied ONLY when the reported uid carries the CloudTAK_Connection_Prefix. Two alternatives were rejected. Normalising both sides into a common canonical key was rejected because it would rewrite the match for every Device, including the native ones that already match correctly, to fix a form only CloudTAK produces. Matching on `ClientEndpoint.username` was rejected because it is a TAK Server account name rather than a Client_Uid, so it would join through an identifier the Device_Table does not hold and would map every Device an account owns onto one connection.

**Scope boundary — this requirement fixes the identifier match and nothing about connection reporting.** Applying the alias gives `chris@chriselsen.net (Web)` a Last_Seen of `2026-08-24T06:40:16.361Z`. It will NOT make that Device render Connected: TAK Server currently reports zero connected clients — `clientEndPoints?showCurrentlyConnectedClients=true` returns an empty list, and all 48 entries read `Disconnected`, the newest `ANDROID-CloudTAK-chris@chriselsen.net` entry included. Whether a CloudTAK browser session is a tracked client endpoint at all is UNVERIFIED. The Connected_Label of Criterion 20.9 therefore remains unverified against the live server for CloudTAK sessions, and this requirement makes no claim that it will appear for one.

#### Acceptance Criteria

1. THE Device_Management SHALL define the Connection_Alias as a pure, total function from one reported `ClientEndpoint.uid` to its Candidate_Client_Uids, returning a value for every input including the empty string, and SHALL place it in ONE shared server-side derivation that both the Last_Seen write and the Connection_Status write call, so the two cannot diverge on which rows a reported uid identifies.
2. THE Connection_Alias SHALL ALWAYS include the reported uid itself in Candidate_Client_Uids and SHALL always try it, so a native ATAK, iTAK, or WinTAK Device — whose certificate `clientUid` and reported `uid` are the same string (verified live, `ANDROID-63040a40563b5fab`) — matches bit-for-bit as it does today; and WHERE the reported uid begins with the CloudTAK_Connection_Prefix compared case-insensitively, THE Connection_Alias SHALL take the base as the remainder of the uid after that prefix and SHALL additionally include `<base> (Web)` and `<base> (ETL)` in Candidate_Client_Uids.
3. THE Connection_Alias SHALL generate BOTH Certificate_Uid_Suffix forms for a prefixed uid rather than choosing one, because the reported uid carries no evidence of which enrollment path minted the certificate and both suffixes are real — ` (ETL)` from upstream `node-tak`, ` (Web)` from the TAK-NZ fork — so selecting one would silently leave the other form unmatched exactly as today.
4. WHEN a poll succeeds, THE Subscription_Poller SHALL target its Last_Seen write at the Candidate_Client_Uids of each reported entry rather than at a single `client_uid`. THE Monotonic_Guard of Criterion 3.3 SHALL be unchanged: this criterion widens which Device_Table rows a statement MAY match and changes nothing about what that statement writes or about the `last_seen_at IS NULL OR last_seen_at < $2` clamp it writes under.
5. WHEN a poll succeeds, THE Subscription_Poller SHALL target its Connection_Status write at the Candidate_Client_Uids of each reported entry rather than at a single `client_uid`, and THE deliberate exclusion of the `connected` write from the Monotonic_Guard required by Criterion 20.3 SHALL be unchanged for the same reason.
6. WHEN a poll succeeds, THE Subscription_Poller SHALL derive the reported set handed to the Criterion 20.6 unreported sweep — the set whose absent `client_uid` values are set to `connected = false` — as the UNION of the Candidate_Client_Uids of every reported entry, rather than as the raw reported `uid` values. This is the one interaction that makes this change non-local and it is load-bearing: a CloudTAK row that Criterion 22.5 has just marked connected is, by construction, absent from the raw reported uids, so a sweep still keyed on those raw values would set it straight back to false inside the same poll and the fix would be invisible. Criteria 20.6's scoping discipline is otherwise unchanged — the write stays restricted to the absent `client_uid` values and is never issued unrestricted by `client_uid`.
7. THE Connection_Alias SHALL NOT map one user's connection onto another user's Device row. Every member of Candidate_Client_Uids is an exact string built from the base, which is the account identifier the connection belongs to; THE Device_Management SHALL match a Candidate_Client_Uid to a Device_Table row by string equality only, and SHALL NOT use prefix matching, substring matching, `LIKE`, or any wildcard, so a row can only be reached by a uid whose base is that row's own account identifier.
8. WHERE a base yields BOTH a `<base> (Web)` row and a `<base> (ETL)` row in the Device_Table, THE Subscription_Poller SHALL write the same Last_Seen and the same Connection_Status to both. This ambiguity is ACCEPTED rather than resolved: TAK Server reports one connection for the account and nothing in the reported entry distinguishes which certificate it was established with, so writing the reported value to both is the honest reading, and is preferred to guessing one and leaving the other stale.
9. THE Connection_Alias is a heuristic keyed on CloudTAK's current string construction, which is upstream code this project does not control. WHERE upstream changes that construction, THE Connection_Alias SHALL stop matching and the affected Device's Last_Seen SHALL return to null — the pre-fix "never seen" behaviour — rather than attaching a timestamp to a different Device. THE Connection_Alias SHALL NOT REPLACE the direct match under any input: an alias candidate is only ever ADDED to the reported uid required by Criterion 22.2, so a construction change can cost a CloudTAK Device its Last_Seen and can never cost a native Device the match it has today.
10. THE Device_Management SHALL correct, in place, the claim in the `server/services/SubscriptionPoller.js` header that `ClientEndpoint.uid` and `tak_devices.client_uid` "live in the same identifier space (verified live, e.g. `ANDROID-842f08e120efdbe3`)". That claim is FALSE: the cited verification sampled a native ATAK device, the one case where the two identifiers coincide by accident. THE Device_Management SHALL edit that sentence to state that the two spaces coincide for native clients and diverge for CloudTAK, and SHALL NOT leave the false sentence standing with a second comment beside it — the same in-place correction convention tasks 25.2 and 28.5 followed.
11. THE Device_Management SHALL document the DN_Shaped_Connection_Uid as known-unhandled at the Connection_Alias derivation site, recording that `MachineConnConfig` and `AdminConnConfig` return `ConnectionControl.uid(cert)` — the certificate subject reversed and comma-joined — and that no uid of that shape appeared in the 48 live Client_Endpoints_API entries, which is why no candidate is generated for it. Recording it as known-unhandled rather than silently ignoring it is the point: a future reader finding an unmatched DN-shaped uid SHALL find it already accounted for rather than mistake it for an oversight.
12. THE Device_Management SHALL cover the Connection_Alias derivation with a fast-check property test asserting that the reported uid is a member of Candidate_Client_Uids for every input, that a uid without the CloudTAK_Connection_Prefix yields exactly that one candidate, that a prefixed uid yields exactly three, and that the derivation returns a value for every input rather than raising; in addition to unit tests over the live examples `ANDROID-63040a40563b5fab`, `ANDROID-CloudTAK-chris@chriselsen.net` → `chris@chriselsen.net (Web)`, and `ANDROID-CloudTAK-ckadmin` → `ckadmin (ETL)`.
13. THE Device_Management SHALL implement this requirement without a Device_Table schema change: the Connection_Alias is computed from the reported uid at poll time and no derived key is persisted, so there is nothing stored that can fall out of date with CloudTAK's construction (Criterion 22.9).
